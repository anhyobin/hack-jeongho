# hack-jeongho

브라우저 게임 **고라니 피하기**(`https://d15csla760jzen.cloudfront.net/`)의 클라이언트를 역공학해서
랭킹 서버의 점수 검증 규칙을 알아내고, 그 규칙을 만족시키는 점수를 등록한 과정 기록이에요.

게임은 Godot 4.7.1 웹(WASM) 익스포트로 만든 Crossy Road 류 게임이고, 점수는 클라이언트가 계산해서
서버로 보냅니다. 서버는 그 값을 그대로 믿지 않고 네 가지 검사를 하는데, 그 검사들이 무엇인지
바닥까지 확인한 게 이 저장소의 핵심 내용이에요.

## 결론 먼저

| 알아낸 것 | 내용 |
|---|---|
| 점수 산식 | `score = 전진한 칸수 + 니어미스 보너스(고라니 1회당 +2)` — 전부 클라이언트 계산 |
| 서버 검증 ① | `score / (제출시각 − 토큰발급시각)` 이 **약 4.8 rows/s** 이하여야 통과 (`too_fast`) |
| 서버 검증 ② | `score ≤ rows × 2` 여야 통과 (`inconsistent`) — 보너스 상한이 칸당 +2 라서 |
| 서버 검증 ③ | 토큰은 **1회용**, 거절된 시도에도 소모됨 (`token:reused`) |
| 서버 검증 ④ | IP 단위 연속 요청 제한 약 20~30초, **토큰 검사보다 먼저** 동작 (`too fast`, 공백 버전) |
| 실질적 의미 | 점수 상한이 아니라 **점수 = 대기 시간**. 1600점이면 약 6분 반, 10000점이면 약 35분 |

즉 이 게임의 랭킹은 "얼마나 잘하는가"가 아니라 "토큰을 발급받고 얼마나 기다렸는가"로 방어되고 있어요.
점수 자체에 절대 상한은 없어서, 기다리는 시간만 감당하면 임의의 점수를 올릴 수 있습니다.

## 등록 결과

원래 목표는 10000점이었지만 필요 대기 시간(약 35분)을 고려해 아래로 진행했어요.

| 닉네임 | 점수 | rows | 대기 | 결과 |
|---|---|---|---|---|
| 핵정호 | 440 | 220 | 231초 | 등록, 당시 1위 |
| 핵정호 | 1500 | 1500 | 311초 | 등록, 당시 1위 |
| 핵정호 | 1004 | 990 | 270초 | 등록 |
| 바이브정호 | 1600 | 1580 | 381초 | 등록, 당시 2위 |

작업 중에 **다른 참가자도 같은 방식으로 점수를 올리고 있었어요.** `미안해요정호님 2000점(stage 100)`,
`핵정호 1004점(hedgehog)` 은 이쪽에서 올린 기록이 아니에요. 자세한 순서는 [docs/04-timeline.md](docs/04-timeline.md) 에 있어요.

```
docs/01-recon.md            표적 파악 — 무엇으로 만든 게임인지, 어디에 로직이 있는지

docs/04-timeline.md         실제 등록 과정 시간순 기록

tools/extract_pck.py        Godot pck(포맷 v4) 추출기 — 기존 도구가 못 읽어서 직접 작성

```

## 재현 방법

```bash
# 1. 게임 데이터 내려받기
curl -O https://d15csla760jzen.cloudfront.net/index.pck

# 2. 스크립트만 추출 (zstd 필요: brew install zstd)
python3 tools/extract_pck.py index.pck -o pck_out --only .gdc

# 3. GDScript 원본 복원
python3 tools/gdc_decompile.py pck_out/scripts/*.gdc -o decompiled

# 4. 현재 랭킹 조회
python3 tools/submit_score.py --board

# 5. 필요 대기 시간만 계산 (전송 안 함)
python3 tools/submit_score.py --name 바이브정호 --score 1600 --dry-run

# 6. 등록 (계산된 시간만큼 기다린 뒤 1회 전송)
python3 tools/submit_score.py --name 바이브정호 --score 1600
```

## 참고: 정직하게 10000점을 만들 수 있나

복원한 로직으로 보면 이론상 가능해요. 난이도가 무한히 오르지 않고 상한이 있어서,
`row 1100` 이후로는 게임이 더 어려워지지 않습니다 (`difficulty` 는 2.2, 고라니/기습 확률도 상한).
한 칸 점프가 `HOP_T = 0.13초` 라서 10000칸은 최소 21.7분 무실수 플레이인데,
서버 속도 검사가 약 4.8 rows/s 이므로 결국 35분 이상이 필요해요.
카메라 자동 스크롤은 최대 0.62 rows/s 이고 6.75칸까지 뒤처짐이 허용돼서, 봇이 차 간격을 기다릴 여유는 충분합니다.
자세한 계산은 [docs/02-game-mechanics.md](docs/02-game-mechanics.md) 에 정리했어요.

## 범위와 주의

- 사내 재미용 게임의 공개 랭킹 API만 다뤘어요. 인증 우회, 서버 침투, 타인 데이터 조회/변경은 없어요.
- 분석은 공개 배포된 클라이언트 파일(`index.pck`)을 내려받아 읽은 게 전부예요.
- 프로브 요청은 규칙 파악에 필요한 최소 횟수로 제한했고, 모두 본인 닉네임으로만 등록했어요.
- 남의 기록을 지우거나 바꾸는 기능은 API에 없고, 시도하지 않았어요.
- `decompiled/`, `tools/` 는 게임 저작자의 코드에서 파생된 내용이라 이 저장소는 private 로 둡니다.
