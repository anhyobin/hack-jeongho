# hack-jeongho

브라우저 게임 **고라니 피하기**(`https://d15csla760jzen.cloudfront.net/`)를 역공학한 기록이다.
Godot 4.7.1 HTML5 익스포트에서 게임 소스 1,880줄을 100% 복원하고, 소스가 없는 랭킹 서버의
검증 규칙을 실측으로 확정한 뒤, 그 규칙을 만족시키는 점수를 실제로 등록했다.

배포된 `index.pck` 하나에서 출발해 다음 세 가지를 얻었다.

1. **게임 전체 소스** — `.gdc`(GDScript 바이너리 토큰) 8개를 원본 줄번호까지 보존해 복원 (`recovered/`)
2. **게임 구조 분석** — 점수 산식, 난이도 곡선과 그 상한, 사망 판정, 서버 계약 (`GAME_STRUCTURE.md`, 1,190줄)
3. **서버 검증 규칙** — 응답 문자열과 통과·거부 경계를 관측해 유도 (`docs/leaderboard-api.md`)

> 클라이언트는 그대로이므로 정직한 플레이어도 등록할 수 없다. 아래 검증 규칙은 **패치 이전**의
> 서버를 기술한 것이다 → [`docs/leaderboard-api.md`](docs/leaderboard-api.md) §6

## 결론

| 항목 | 내용 |
|---|---|
| 점수 산식 | `score = 전진 칸수 + 니어미스 보너스(고라니 1회당 +2)` — 전부 클라이언트 계산값 |
| 서버 검증 ① | **`rows`** / 토큰 나이 가 약 **9 행/초** 이하여야 통과 (`403 too_fast`) — `score`가 아니다 |
| 서버 검증 ② | `score ≤ rows × 2 + 40` 여야 통과 (`403 inconsistent`) |
| 서버 검증 ③ | 토큰은 **1회용**, 거부된 시도에도 소모된다 (`token:reused`) |
| 서버 검증 ④ | IP 단위 제출 스로틀, **토큰 검사보다 먼저** 평가된다 (`429 too fast`) |
| 실질적 의미 | 점수에 절대 상한이 없다. 제약은 **칸수 = 대기 시간** 하나뿐이다 |

정직한 플레이의 상한은 대략 400점이다(사람 최고 기록 `민지 401점`). 반면 토큰을 발급받고
기다리기만 하면 임의의 점수를 올릴 수 있다. 즉 이 리더보드를 지키는 것은 점수 검증이 아니라
**실시간 대기 시간**이다.

그리고 그 대기 시간을 결정하는 것은 `score`가 아니라 `rows`다. 두 검사를 합치면
**`score_max ≈ 17.6 × 경과초 + 40`** 이므로, `rows`를 점수의 절반으로 두면 대기가 절반이 된다 —
10,001점이 26분이 아니라 **9.5분**에 들어간 이유다. 이 한 가지를 몰랐던 08-12 세션은
같은 목표를 "너무 오래 걸린다"며 포기했다.

3,000점은 규칙의 예측력을 그대로 시험한 것이다. 안전 대기값 469초에 11초를 얹은 480초에서
**첫 시도로 통과**했다 — 탐색용 프로브 없이 한 번에 맞췄다.

10,001점은 그보다 한 걸음 더 나갔다. 보드에 먼저 올라온 남의 항목(`10000 / rows 4980`)이
정합성 경계에 정확히 붙어 있는 것을 보고 **속도 검사가 `rows`를 본다**는 가설을 세웠고,
`rows = 5001`로 낙관적인 나이부터 시도해 **첫 시도(565.6초)에 통과**했다. `score` 기준 비율
17.68/s가 통과한 이상 `score` 기준 규칙은 성립할 수 없으므로, 이 한 건이 가설을 확정한다.

원래 목표였던 10,000점을 08-12에 포기한 이유가 그래서 잘못된 계산이었다는 것도 함께 드러났다.

`불꽃미남정호 10000`과 `t`의 항목들은 이 작업이 올린 것이 아니다. `호호호 2500`에는
클라이언트가 보내지 않는 `admin_insert: true` 키가 붙어 있어, **서버 운영자에게 POST 검증을
우회하는 삽입 경로가 있다**는 사실도 여기서 드러났다.

### 한 번의 GET을 증거로 삼지 않는다

13:14에 `GET api/scores`가 640점 초과 항목 11개가 빠진 목록을 돌려줬다. "운영자가 고득점을
전부 지웠다"로 읽혔지만, 저장해 둔 스냅샷과 레코드 단위로 대조하니 **같은 목록이 오프셋만
밀린 것**(`filtered[0:39] == full[11:50]`)이었고 2분 뒤 원상복구됐다. 그 사이 시작했던
재등록은 첫 POST 90초 전에 중단했다 — 재폴링 없이 밀어붙였다면 라이브 서버에 회수 불가능한
항목을 하나 더 남겼을 것이다.

### 두 세션이 서로를 제3자로 오인했다

같은 시각에 두 개의 작업 세션(A, B)이 같은 게임을 독립적으로 파고 있었고, **서로가 남긴 기록을
각각 "제3자의 침입"으로 기록했다.** 둘 다 같은 사람의 작업이다. 리더보드에는 등록자를 식별할 정보가
없어서(닉네임은 임의 문자열) 구분 단서는 캐릭터뿐이었는데, 그마저도 세션 A가 마지막 2000점을
`peccy`로 올려서 무너졌다 — A는 `hedgehog` 3건 + `peccy` 1건, B는 전부 `peccy`다.

부수적으로 얻은 검증이 하나 있다. 두 세션이 각각 독립적으로 작성한 `.gdc` 디컴파일러의 출력이
**토큰 단위로 완전히 일치**했다(차이는 빈 줄과 `:=` 앞 공백뿐). 복원 결과를 신뢰할 근거가 된다.
줄번호까지 보존하는 세션 A 버전을 `recovered/`의 정본으로 채택했다.

## 재현

**Python 3.14+ 필요** — `gdc_decompile.py`가 `from compression import zstd`(3.14 stdlib)를 쓴다.

```bash
cd _dl && curl -O https://d15csla760jzen.cloudfront.net/index.pck

python3 unpack.py > ../unpacked_manifest.txt      # GDPC 언팩 -> _dl/extracted/ (110개)
cd extracted/scripts && python3 ../../gdc_decompile.py *.gdc   # .gdc -> .decompiled.gd

python3 tools/board_probe.py <대기초> <score> [rows] [name] [char]   # 단발 프로브
python3 tools/submit_target.py <score> <name> [char] [나이,목록] [rows]  # 목표 점수 숙성 스케줄러
#   rows를 반드시 넘길 것 — 생략하면 rows=score가 되어 대기가 두 배가 된다
```

`gdc_decompile.py`가 출력하는 `leftover=0`이 복원 완전성의 근거다. 0이 아니면 그 출력은 신뢰할 수 없다.

## 범위

- 공개 배포된 클라이언트 파일과 공개 랭킹 API만 다뤘다. 인증 우회, 서버 침투, 타인 데이터 접근은 없다.
- 쓰기 요청은 규칙 확정에 필요한 최소 횟수로 제한했고, 전부 [`docs/submissions-log.md`](docs/submissions-log.md)에 기록했다.
- **삭제 엔드포인트가 없다.** 등록된 기록은 회수할 수 없으므로 남은 항목도 그대로 기록해 뒀다.
- 남의 기록을 지우거나 변경하는 기능은 API에 존재하지 않으며, 시도하지 않았다.
- `recovered/`는 게임 저작자의 코드에서 파생된 결과물이므로 이 저장소는 private으로 유지한다.
