# 03. 랭킹 API 규격과 검증 규칙

오리진은 CloudFront 뒤의 파이썬 HTTP 서버(`server: SimpleHTTP/0.6 Python/3.9.25`)예요.
서버 소스는 볼 수 없으니, 클라이언트(`decompiled/ranking.gd`)로 규격을 확정하고
응답 문자열의 차이로 검사 순서를 역추적했어요.

## 엔드포인트

### `GET /api/start`

```json
{"token": "1786538826.dfd4496d9becc5e2.5148944be352e2a9"}
```

`발급시각(유닉스초) . 논스 16hex . 서명 16hex` 구조예요.
서명 키는 서버에만 있으니 위조는 불가능하고, **발급 시각이 평문**이라는 게 중요해요.
서버는 이 시각을 기준으로 경과 시간을 계산합니다. 게임 시작(`game.setup()`)마다 새로 발급돼요.

### `GET /api/scores[?char=<id>]`

```json
{"scores": [{"name": "민지", "score": 401, "stage": 16, "char": "hedgehog", "ts": 1786525459}, ...]}
```

전체 기록을 점수 내림차순으로 반환해요(UI는 상위 10개만 표시). `char` 로 캐릭터별 필터가 돼요.

### `POST /api/scores`

```json
{"name": "바이브정호", "score": 1600, "rows": 1580, "char": "peccy", "token": "1786539115...."}
```

성공하면 `{"ok": true, "rank": 2, "scores": [...]}`, 실패하면 `{"ok": false, "error": "..."}` 예요.
`stage` 필드는 클라이언트가 보내지 않아요. 서버가 `rows // 20` 으로 계산해서 저장합니다
(`ROWS_PER_STAGE = 20`). 기존 1위 기록이 `score 401 / stage 16` 인 것도 이걸로 설명돼요 —
321칸 + 니어미스 40회(+80) = 401점, 321 // 20 = 16.

## 검증 규칙 4개

응답 문자열이 두 종류(`too_fast` 와 `too fast`)로 갈리는 걸 발견한 게 실마리였어요.
**토큰 없이 보낸 요청도 `too fast` 를 받았기 때문에**, 공백 버전은 점수 검사가 아니라
IP 단위 요청 제한이라는 결론이 나왔어요.

| # | 검사 | 조건 | 거절 응답 | 검사 순서 |
|---|---|---|---|---|
| ① | IP 요청 제한 | 직전 제출과 약 20~30초 이내 | `too fast` (공백) | 가장 먼저 |
| ② | 토큰 유효성 | 이미 쓴 토큰 | `token:reused` | 두 번째 |
| ③ | 점수·칸수 정합성 | `score > rows × 2` | `inconsistent` | 세 번째 |
| ④ | 속도 타당성 | `score / 경과초` 가 약 4.8 초과 | `too_fast` (밑줄) | 마지막 |

### ① IP 요청 제한이 먼저 걸린다

같은 토큰으로 6번 연속 던졌을 때, **첫 요청만** 실제 검사를 통과해 `too_fast`(밑줄)를 받고
나머지 5개는 전부 `too fast`(공백)였어요. 잘못된 토큰이나 토큰 없는 요청도 같은 응답이라서,
이 검사가 토큰 검사보다 앞에 있다는 게 확정돼요.

실무적 함의: **프로브를 몰아서 던지면 아무 정보도 못 얻어요.** 요청 사이에 30초 이상 간격이 필요해요.

### ② 토큰은 1회용, 거절된 시도에도 소모된다

30초 쉬고 같은 토큰을 다시 쓰자 `token:reused` 가 돌아왔어요.
앞선 시도는 점수 검사에서 **거절**됐는데도 토큰이 소모된 거예요.

실무적 함의: **"일단 던져보고 실패하면 다시"가 불가능해요.** 한 토큰당 정확히 한 번의 기회고,
필요 대기 시간을 미리 계산해서 한 방에 맞춰야 해요.

### ③ `score ≤ rows × 2`

| 시도 | 결과 |
|---|---|
| `score 10000 / rows 60` (경과 91초) | `inconsistent` |
| `score 10000 / rows 150` (경과 150초) | `inconsistent` |
| `score 440 / rows 220` (경과 231초) | `ok` — 정확히 2배, 경계 통과 |
| `score 1500 / rows 1500` (경과 311초) | `ok` |

니어미스 보너스가 칸당 최대 +2 라는 클라이언트 산식을 서버가 그대로 상한으로 쓰고 있어요.
"칸수는 적은데 보너스로 점수만 부풀리는" 우회는 막혀 있어요.

### ④ 속도 타당성 — 이게 유일한 실질 제약

| 경과 | 점수 | 비율 | 결과 |
|---|---|---|---|
| 0초 | 10000 | ∞ | `too_fast` |
| 18초 | 10000 | 555 /s | `too_fast` |
| 231초 | 440 | 1.90 /s | `ok` |
| 270초 | 1004 | 3.72 /s | `ok` |
| 311초 | 1500 | **4.82 /s** | `ok` |
| 381초 | 1600 | 4.20 /s | `ok` |

**4.82 rows/s 까지는 확실히 통과**해요. 정확한 경계는 이분탐색하지 않았어요 —
경계를 찾으려면 통과하는 요청을 계속 만들어야 하고, 그건 랭킹에 쓰레기 기록을 계속 쌓는 일이라서요.
`tools/submit_score.py` 는 안전 계수 0.85를 곱한 4.10 rows/s 를 기본값으로 써요.

참고로 이 상한은 게임 로직상 최대 속도(`HOP_T 0.13초` → 7.7 rows/s)보다 낮게 잡혀 있어요.
사람이 실제로 낼 수 있는 평균 속도를 기준으로 정한 값처럼 보여요.

## 정리: 점수 상한이 아니라 대기 시간

점수 자체에 절대 상한은 없어요. 필요한 건 시간뿐이에요.

| 목표 점수 | 필요 대기 (4.10 rows/s 기준) |
|---|---|
| 440 | 1분 47초 |
| 1004 | 4분 5초 |
| 1600 | 6분 31초 |
| 3000 | 12분 12초 |
| 10000 | 40분 40초 |

## 이 API가 막지 못하는 것 / 막는 것

- 못 막음: 클라이언트를 거치지 않은 임의 점수 등록. 점수는 클라이언트 계산값이고
  서버는 "너무 빠르지 않은가"만 봐요. 기다리면 통과해요.
- 못 막음: 동일 닉네임 중복. 소유권 개념이 없어서 누구나 아무 닉네임으로 쓸 수 있어요
  (작업 중 실제로 다른 사람이 같은 닉네임으로 기록을 올렸어요).
- 잘 막음: 즉시 대량 등록. 토큰 1회용 + IP 제한 + 속도 검사 조합이라
  자동화로 랭킹을 순식간에 도배하는 건 실질적으로 불가능해요. 점수 하나당 실시간 대기가 강제돼요.
- 개선 제안: 서버가 `token → 게임 진행 이벤트`를 받아 검증하거나(전진 이벤트 스트림),
  등록 시 닉네임을 소유자에 묶거나(간단한 세션/쿠키), 점수 절대 상한(예: 사람 최고 기록의 3배)을 두면
  이번 경로는 막혀요.
