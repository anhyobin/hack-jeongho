# 게임 안에 오토파일럿을 심는 길 — pck 재패킹과 완전정보 봇

08-14 02:16 패치로 **점수를 만드는 방법은 실제로 행을 넘는 것뿐**이 됐다(서버가 시드로 trace를
재현한다 — [`leaderboard-api.md`](leaderboard-api.md) §7·§8). 그래서 필요한 것은 제출 도구가
아니라 **플레이어**다. 이 문서는 그 플레이어를 게임 안에 심은 방법과, 그 과정에서 확정한 게임
내부 규칙을 기록한다.

시야(픽셀)로 화면을 읽는 봇은 앞선 세션이 시도해 12행에서 멈췄다(`tools/js/autopilot.js`).
여기서는 아예 **게임 코드 안으로 들어가** 차량 좌표·기차 위상·막힌 칸을 직접 읽는다.

## 1. 평문 `.gd`를 pck에 다시 넣을 수 있다

익스포트된 pck에는 `scripts/game.gdc`(바이너리 토큰)와 `scripts/game.gd.remap`이 쌍으로 들어 있고,
remap이 `res://scripts/game.gd` → `res://scripts/game.gdc`로 로드를 돌린다. Godot의 GDScript
로더는 **확장자로 소스와 토큰 버퍼를 구분**하므로, remap을 지우고 같은 경로에 평문 `.gd`를 넣으면
런타임에 그대로 파싱·컴파일된다. 즉 **디컴파일한 소스를 고쳐서 다시 심을 수 있다.**

```bash
python3 tools/pack.py --verify      # 원본 재패킹 → 바이트 동일 (포맷 검증)
python3 tools/make_bot_patch.py     # 디컴파일 결과 + 봇 → patch/{game,main}.gd
python3 tools/pack.py -o _local/index.241563a7.pck \
        --text scripts/game.gd=patch/game.gd --text scripts/main.gd=patch/main.gd
```

주의할 점 세 가지.

- **경로를 바꾸지 말 것.** `.godot/global_script_class_cache.cfg`가 `class_name`을
  `res://scripts/game.gd`에 묶어 두므로, 다른 경로에 같은 `class_name`을 두면
  "hides a global script class"로 파싱이 실패한다. remap을 지우고 **같은 경로**에 평문을 넣는다.
- **`index.html`의 `fileSizes`를 함께 고친다.** 로더가 pck 크기를 진행률 계산에 쓴다.
- `tools/pack.py`는 `--verify`로 원본을 바이트 단위 복원한다. 이 성질이 깨지면 정렬 규칙이나
  헤더 상수가 틀린 것이므로 출력물을 믿어선 안 된다. 알아낸 레이아웃은
  [`toolchain.md`](toolchain.md)에 있다 — 특히 **pack_format_version 4는 경로에서 `res://`를
  떼어 저장**하고, **데이터 배치 순서가 디렉터리 순서와 다르다**(원본 오프셋 순서를 유지해야 한다).

## 2. 봇이 지켜야 하는 불변식 — rng를 건드리지 않는다

서버는 `api/start`의 시드로 월드를 재현해 우리 trace를 되돌린다. 월드는 `Game.rng` 소모 순서의
함수이므로, 봇이 `rng`를 한 번이라도 더 쓰거나 `_gen_row()`를 직접 부르면 **서버의 재현과 어긋나
제출이 거부된다.** 그래서 봇은

- 관측은 전부 **읽기 전용**(`rows[i].entities`, `rail_phase`, `blocked` …)
- 행동은 사람의 손가락과 똑같이 **`try_move()`로 `pending_input`만 세운다**
- 지터용 난수는 **별도 `RandomNumberGenerator`**(`brng`)를 쓴다 — 화면 흔들림이 `vrng`를 따로
  쓰는 것과 같은 이유다

`main.start_game(char_id, forced_seed)`와 `claim_run(forced_seed)`가 클라이언트에 살아 있어,
**토큰 없이 임의 시드의 월드를 재생**할 수 있다(`?bseed=`). 월드가 시드만의 함수이고 봇 판단이
틱 상태만 보므로 **같은 시드 = 같은 주행**이다. 실서버 시드로 미리 연습해 성공을 확정한 뒤 본
주행을 돌리는 길이 열려 있다(이번에는 쓰지 않았다).

## 3. 결정적으로 중요한 규칙 — 홉 중에는 hazard 검사를 건너뛴다

`game.gd:208`이 `if not player.hopping and not player.dead:` 조건에서만 `hazard_hit`을 부른다.
`HOP_TICKS = 8`이고 착지 틱에 `_resolve_landing`이 한 번 더 검사하므로,

> **8틱마다 끊기지 않고 전진하면 중간 행은 착지하는 한 틱만 위험에 노출된다.**

그래서 "도로 위에서 안전하게 기다릴 수 있는가"를 물을 필요가 없다. 안전한 풀밭에서
**다음 풀밭까지의 구간 전체**를 한 번에 검사해 통째로 건너면 된다. 봇의 사망은 전부 위험한 행에
서 있다가 갇힌 것이었고, 정책을 이 구조로 바꾼 뒤 도달 행수가 20~90행에서 **240~354행으로** 뛰었다.

대기 여유도 넉넉하다. 스크롤 사망 조건은 `568 + (cam_row - row) * 64 > 1000`, 즉
`cam_row - row > 6.75`이고 홉 직후 `cam_row ≈ max_row - 3`이므로 **한 칸에서 약 15초를 버틸 수
있다**(자동 스크롤 상한 0.62행/초). 즉 "확실히 안전할 때만 움직인다"가 감당 가능한 규칙이다.

## 5. 봇 파라미터

URL 쿼리로 켠다. 게임은 `tools/local_proxy.py`가 `127.0.0.1`에서 서비스한다.

| 파라미터 | 뜻 |
|---|---|
| `bot=1` | 자동 조종 켜기 |
| `bt=<점수>` | 이 점수에 도달하면 정지(그 뒤 스크롤 사망을 기다린다) |
| `br=<행>` | 행수 기준 정지. **점수를 부풀려 제출하는 데는 쓸 수 없다**([`leaderboard-api.md`](leaderboard-api.md) §8.1) |
| `bn=<닉네임>` | 제출 닉네임 (URL 인코딩) |
| `bsub=1` | 목표 도달 시 자동 제출 |
| `bloop=1` | 죽으면 자동 재시작. 제출이 성공하면 멈춘다 |
| `bchar=<id>` | 캐릭터 (`peccy` 등) |
| `bseed=<정수>` | 토큰 없이 그 시드를 재생(연습용, 제출 불가) |
| `bdump=1` | 난수·행 데이터 덤프(포팅 검증용) |

체크포인트 탐색용 파라미터(`ss`·`sv`·`sspd`·`sdrop`·`sttl`·`smin`·`stok`·`sseed`)는 §8.8에 있다.

연습은 실서버를 건드리지 않는다.

```bash
MOCK_START=1 BLOCK_POST=1 PORT=8777 python3 tools/local_proxy.py
# → http://127.0.0.1:8777/?bot=1&bt=99999&bloop=1&bchar=peccy
```

## 8. 체크포인트 탐색 — 죽은 지점을 되감아 구간별로 조립한다 (602점)

§6의 봇은 200점(약 190행)을 3회에 1회 낸다. 600점에는 550행이 필요한데, 한 주행으로
550행을 무사고 통과할 확률은 그 분포에서 사실상 0이다. **그래서 주행을 통째로 버리지 않는다.**

> 월드는 시드만의 함수다. 죽으면 **죽은 지점 앞까지의 trace를 고속 재생해 상태를 정확히
> 복원하고**, 거기서 다른 지터로 이어서 주행한다. "550행을 한 번에"가 "10~20행씩 여러 번"이 된다.

구현은 `patch/bot_search.part.gd`(하네스, `main.gd` 뒤에 붙는다)이고, 실측 결과는
[`wt-notes/wt-search.md`](wt-notes/wt-search.md)의 작업 기록에 회차별로 남아 있다.

### 8.1 회차별 도달 행 — 프런티어는 단조 증가한다

```
연습 seed 777001   [108, 108, 108, 108, 548]                    5회차 / 7초   -> 600점
연습 seed 424242   [256, 319, 318, 310, 478, 478, 556]          7회차 / 20초  -> 600점
실서버 seed 2284936702885992
                   [22, 22, 22, 22, 58, 58, 58, 58, 108, 190, 413, 562]
                                                                12회차 / 15초 -> 602점
```

같은 지점에서 몇 번 막히다가 **되감기가 깊어지는 순간 수십~수백 행이 한꺼번에 열린다**
(190 → 413 → 562). 봇의 사망은 국소적이므로, 그 지점만 다른 갈래로 통과하면 뒤는 이미
통과할 수 있는 구간이다.

### 8.2 고속 재생이 전제다

12,000틱 접두사를 60틱/초로 재생하면 200초다. 40회 반복은 2시간이 넘는다. 원본
`_process`의 프레임당 틱 상한(`MAX_TICKS_PER_FRAME = 8`)을 `main.bot_tick_ok(self, guard)`로
치환해 하네스가 정한다(`tools/make_bot_patch.py`의 `replace` 모드).

**시뮬레이션 의미는 바뀌지 않는다** — 같은 `FIXED_DT`, 같은 틱 순서, 같은 `rng` 소모다.
그래서 재생 동일성이 60배속에서도 정확히 성립한다(2,236틱 = 1.5초 @ 25배속).

`bot_tick_ok`가 조건의 **맨 앞**에 오는 것이 설계다. `state != "play"`가 된 직후에도 한 번
더 불리는 것이 **사망 틱 훅**이고, 거기서 즉시 다음 주행을 띄우면 `on_game_over`의 1초
타이머가 깨어날 때 `_over_token`이 이미 달라져 있어 그 뒤의 **`ranking.start_run()`이
실행되지 않는다.** 주행마다 `api/start`가 한 번씩 새는 것을 막는 유일한 지점이다 —
순서를 바꾸면 40회 주행에 40번 토큰을 발급하고 실제 토큰·시드도 날아간다.

### 8.3 되감기는 "홉 몇 개"가 아니라 "어느 행"이다

처음에 `_search_prefix`를 "꼬리에서 전진 홉 N개를 버린다"로 썼더니 **34회 연속 제자리**였다
(접두사 62행 → rows 62, 증가 0). 봇은 죽기 전에 비상 분기로 앞뒤로 진동하므로 **꼬리의
전진 홉을 버려도 최고 도달 행이 그대로 남는다.** 지금은 trace를 앞에서부터 누적해
(`0=전진 +1`, `1=후진 -1`) 최고점에서 `drop_rows`행 아래에 **처음 닿는 지점**에서 자른다.

되감기 폭도 훑어야 한다. 실패가 쌓일 때 단조 증가시키면 한 번 깊어진 뒤 얕고 싼 되감기를
다시 못 본다 — `search_drop + rand(0,3) + (search_fail % 12) * 4`로 6~53행을 순환한다.

### 8.4 같은 접두사에서 다른 갈래를 보게 하는 손잡이

인계 시점에 **첫 홉 시각만 흔든다**: `g.bot_hop_t = g.tick_count + rand(0, 12)`.
`brng`의 `bot_gap ∈ {8, 9}`와 합쳐져 갈래가 갈린다. `_bot_decide` 내부는 블랙박스로 둔다.

**trace에 합성 입력을 끼워 넣는 방식은 쓰지 않았다** — 서버가 각 항목을 어떻게 보는지
모르는데 bump가 될 수도 있는 가짜 입력을 넣을 이유가 없다.

### 8.5 재생 동일성이 첫 관문이다 (탐색보다 먼저)

`?sv=1`이 한 방으로 세 주행을 잇는다: 1차 주행 → 같은 시드로 그 trace 재생 → 변이 재생.

```
[gate] 1차 주행 rows=67 score=71 ticks=2236 trace=78건
[gate] 2차 재생 rows=67/67 score=71/71 ticks=2236/2236 -> 동일 PASS
[gate] 변이 재생 rows=2 (원본 67) -> 줄었다 PASS
```

★ **변이 검증에는 함정이 있다.** "한 항목의 틱을 +1하면 입력이 버려진다"는 무조건 참이
아니다. **앞 홉과의 간격이 정확히 8틱인 항목**을 골라야 한다 — 그러면 늘린 틱에 플레이어가
홉 중이라 `_consume_input`이 아예 불리지 않고 `replay_idx`가 그 항목에 걸려 뒤 입력이 전부
버려진다. 간격 9인 항목을 고르면 1틱 지연으로 끝나 `rows`가 줄지 않는다.

### 8.6 탐색이 벽시계보다 빠르므로 제출 전에 토큰을 늙힌다

12,478틱은 208 시뮬레이션초인데 25초에 돈다. 서버는 나이로도 판정하므로
(`rows <= elapsed * 9.5`, 그 밖의 나이 검사가 더 있어도 이상하지 않다) 제출 직전에
`max(rows/9.4, ticks/60) + 45`초까지 기다린다. 토큰의 **첫 필드가 발급 epoch**이라 나이를
클라이언트가 직접 계산할 수 있다. 실측 `elapsed 253.4`로 통과했다.

### 8.7 오제출 4중 가드

탐색은 수십 회 주행하므로 실수로 낮은 점수가 나가는 것을 구조적으로 막아야 한다.

1. 탐색 주행은 `claim_run(forced_seed)` → `active_token == "TEST"` → `submit`이 즉시 "offline"
2. `game.bot_submit = false`
3. `game.bot_name = ""`
4. 최종 제출은 `bsub=1` · 닉네임 · 실제 토큰 **세 개가 모두** 있어야 나간다

실서버 접촉은 결국 **`api/start` 1회 + `POST` 1회**였다. 나머지는 전부 모의 프록시다.

- 사망 원인별 되감기 전략이 없다. `[dead] kind=` 로그가 있으니 강(익사)·레일(기차)에 따라

## 9. 오프라인 시뮬레이터 — 서버가 하는 재현을 우리도 한다

§8의 체크포인트 탐색은 엔진을 오라클로 쓴다. 그것과 **독립적으로**, 월드를 파이썬으로 재현해
경로를 계산으로 합성하는 길도 열렸다(`tools/sim.py` + `tools/solve.py`).
경위는 [`wt-notes/wt-rng.md`](wt-notes/wt-rng.md)의 작업 기록에 있다.

```
python3 tools/rng_probe.py                       난수 정답지 검사 (exit 0이어야 한다)
python3 tools/sim.py /tmp/valcases.jsonl         실제 주행 재현 대조 (6/6 일치)
python3 tools/solve.py <시드> --target 600 --width 8    빔 탐색 → trace + ticks
```

실측: 시드 2개에서 각각 261초·274초에 600점 trace를 합성했다(`rows 570 / 584`, 자체 검산 통과).

### 9.1 난수에서 틀렸던 것 셋 — 하나라도 틀리면 전부 어긋난다

`4.7.1-stable` 원본 기준이고, CLAUDE.md에 요약이 있다.

1. **`rng.seed = N`은 `state = N`이 아니다.** `pcg32_srandom_r(&pcg, N, current_inc)`이다 —
   state 0에서 `inc = (PCG_DEFAULT_INC_64 << 1) | 1`로 한 번 전진, 시드를 더하고, 다시 전진.
   그래서 `seed 0`의 첫 `randf()`가 `0.0`이 아니다.
2. **`randf()`는 `rand()`를 두 번 먹는다** — `ldexp((float)(rand() | 0x80000001), -32 - clz32(proto))`.
   `rand() / 0xFFFFFFFF`가 아니다. **난수 소비 개수가 두 배로 다르다.**
3. **`randi_range`는 기각 표본이다**(`pcg32_boundedrand_r`, `threshold = -n % n`).
   `rand() % n`과 2의 거듭제곱에서만 같고 **9·7·6·5·3에서 갈라진다** — 풀밭 Fisher-Yates가
   정확히 그 경우다. `randi_range(a, a)`는 난수를 **소모하지 않는다**.

★ 앞선 세션은 **맞는 시딩을 이미 시도했는데도** 배제했다 — 판정을 **틀린 `randf`로** 했기
때문이다. **가설을 배제할 때는 시험의 나머지 조건이 맞는지 확인해야 한다.** 아니면 배제 표
전체가 무효다. `tools/rng_probe.py`가 시딩 7종 × `randf` 3종 격자를 한 번에 돌려 이 함정을 막는다.

### 9.2 재현이 맞는지 어떻게 아는가

사망 틱까지 일치시키는 것이 기준이다. 검증 6건이 `rows`·`score`·`ticks`(2881·2039·3401·3340·
4387·2677)·`cause`까지 전건 일치하고, 사인 4종(scroll/train/gorani/car)과 니어미스 보너스가
붙은 건까지 포함한다. **사망 틱이 맞으면 그 앞의 모든 틱이 맞은 것이다.**

변이 검증도 했다 — `_build_grass`의 장식 `randf_range` 하나를 지우면 6건 전부 3행에서
어긋나고, 되돌리면 6/6으로 복귀한다.

그리고 **합성한 trace를 엔진이 채점하게 해 교차 검증했다**(`?brep=1`로 `_local/trace.json`을
`replay_mode`에 먹인다). 우리 예측 `rows 590 / score 600 / ticks 7259 / cause car`와
엔진 실측이 **완전히 일치**했다.

### 9.3 탐색에서 정체의 원인은 게임이 아니라 탐색 버그였다

- **DFS는 프런티어에 갇힌다.** 막힌 행에서 부분나무를 다 뒤지느라 위로 못 올라간다(359행에서
  6분, 노드 37만 개). 체크포인트를 여러 개 살리는 **빔**으로 바꾸니 같은 행을 정체 없이 지났다.
- ★ **막힌 이동(bump)을 후보로 두면 안 된다.** `player.bump()`는 시계만 1틱 흘리고 상태를
  바꾸지 않으므로 `("wait", 1)`과 같다. 그런데 "가장 싼 행동"이라 동점 정렬에서 항상 이겨,
  막힌 열에서 **전진만 무한 반복**했다. 후보에서 빼자 7행 영구 정체가 60초에 137행이 됐다.
- **확장 단위는 행 단위 복합 행동**이다(`k틱 대기 후 이동`, k는 6틱 격자). 행동을 하나씩
  확장하면 빔이 "같은 자리에서 2~3틱씩 다르게 기다린 상태"로 채워져 다양성이 붕괴한다.
- **후퇴도 후보에 넣어야 한다**(스크롤 여유 3행 이상일 때만). 빼 두면 앞·좌·우가 모두 막힌
  덫에서 빔이 통째로 전멸한다(시드 4376317247726913의 127행에서 실측).

### 9.4 이 경로는 아직 제출에 쓰지 않았다

`sim.py`가 클라이언트와 틱 단위로 일치하므로 서버의 재현과도 일치할 것으로 보지만 **실측되지
않았다(추정).** 제출하려면 §8.6과 같이 토큰 나이를 맞춰야 한다(600점 ≈ 590행이면
`rows <= elapsed * 9.5`에서 63초 이상). 오프라인 합성은 주행 시간이 들지 않으므로 시드를 받고
기다리기만 하면 된다.

## 10. 프로토콜 v4 대응 — 청크 시드와 "행 생성은 한 틱도 늦어선 안 된다"

08-14 22:04 배포로 월드 시드가 **25행 단위 청크**로 쪼개졌다(계약은
[`leaderboard-api.md`](leaderboard-api.md) §10). §8의 방법 자체는 그대로 성립하지만
하네스가 세 가지를 더 지켜야 한다. 이 절은 그 세 가지와, 그 과정에서 확정한 규칙을 남긴다.

### 10.1 탐색 주행도 실토큰으로 돌아야 한다 — 그래서 가드가 게임 밖으로 나갔다

`Ranking.want_chunk`는 `active_token == "TEST"`를 걸러낸다. 즉 `claim_run(forced_seed)`로
띄운 연습 주행은 프런티어에서 새 청크를 받아올 수 없다. 탐색 주행이 실토큰을 들고 돌아야
하므로 §8.7의 1번 가드("TEST 토큰이라 제출이 구조적으로 불가능")가 사라졌다.

그 자리를 **프록시가 게임 밖에서** 메운다.

```bash
ALLOW_POST_NAME=<닉> ALLOW_POST_MIN_SCORE=<점수> python3 tools/local_proxy.py
#   조건에 맞지 않는 POST api/scores는 중계 자체를 하지 않는다 (403 blocked-locally)
```

이쪽이 옛 가드보다 강하다 — 게임 안의 어떤 실수도 이 조건을 통과하지 못한다.
`BLOCK_POST=1`은 이제 `api/scores`만 막는다. **`api/chunk`를 막으면 월드를 서버에서 못 받아
주행이 통째로 `unranked`가 되므로** 연습에서도 막아선 안 된다(그래서 `MOCK_START=1`이
`api/chunk`까지 모의 응답한다).

수확한 청크 시드는 **회차 간 누적해야 한다.** `claim_run`이 매 주행 `active_chunks`를
`chunks`에서 새로 복사하므로, `_search_launch`가 그 자리에 누적분을 되돌려 놓는다.
거두는 것을 한 곳이라도 빼먹으면 같은 청크를 계속 다시 받는다 — 실측에서 청크 8을
**18번** 다시 받았다(시드는 (토큰, 청크)만의 함수라 값은 매번 같았다).

### 10.2 ★ 행 생성이 한 틱 늦으면 그 주행은 버려야 한다

`_sim_tick`은 `rows`에 **들어 있는** 행만 `step(dt, self)`한다. 시드가 없어 `_gen_row`가
false를 돌려주면 그 행은 다음 틱에 만들어지고 **`step()`을 한 번 덜 받는다.** 서버는 시드를
모두 쥔 채 재현하므로 그런 지연이 없다.

실측이 잔혹하다 — 그런 trace를 같은 시드로 재생하면 **438행 접두사가 241행에서 죽었다.**
1틱 차이가 차량 2~3px이고 히트박스 여유보다 작아 보이지만, 600행을 가는 동안 어디선가
생사를 가른다.

반면 **틱 전체를 멈추는 것은 시뮬레이션에 보이지 않는다** — 배속을 올리는 것과 같은 성질이다
(§8.2). 그래서 하네스는 **경계에 닿기 전에 틱을 멈추고** 시드를 받은 뒤 이어 간다.
`_sim_acc`도 함께 비운다.

> `_sim_acc`를 **무조건** 비우면 안 된다. "틱 하나만 흘려서 원본이 재요청하게 한다"가
> 한 틱도 돌지 않아 교착에 빠진다(실측: 75초 동안 재요청 0건). 대기 중에만 비우고,
> 한 틱을 흘릴 때는 `_sim_acc = FIXED_DT`로 **정확히 한 틱만** 준다.

### 10.3 요청 시점에는 창이 있고, 우리는 그 창을 못 맞췄다

`api/chunk`는 trace를 재현해 검증하므로 요청 시점의 도달 행이 중요하다. 창의 아래끝은
"직전 청크의 첫 행"으로 보인다(청크 9가 204행에서 발급됐다). 하네스는 아래끝+2에서
요청하고, 거부되면 +4씩 깊게 옮기며 **생성이 막히기 직전까지** 훑는다(그 지점을 넘기면
§10.2의 지연이 생긴다).

이 보정은 실제로 동작한다 — 연습에서 아래끝+2가 거부되고 **+6에서 확보**된 뒤 이후 청크가
전부 통과했다. 그런데 **실서버에서는 어떤 깊이로도 통과하지 못하는 청크가 나온다**
(+2·+6·+10·+14·+18 전부 `403`). 토큰마다 그 지점이 다르고(27 / 4 / 9 / 6) 한 번 막히면
영구히 막힌다. 원인은 확정하지 못했다 — 유력한 추정은 `api/chunk`의 IP 단위 제한 소진이다
([`leaderboard-api.md`](leaderboard-api.md) §10.3에 표와 배제 근거를 정리했다).

### 10.4 §8.5의 변이 검증은 **방향이 반대로** 적혀 있었다

"간격 8틱인 항목의 틱을 **+1** 하면 입력이 버려진다"는 틀렸다. `hop_end_tick = 시작 + 8`이고
홉은 그 틱에 끝나므로, 간격 8을 9로 만드는 것은 **홉이 끝난 다음 틱에 소비되는 1틱 지연**일
뿐이다. 결과가 그대로일 수 있고, 실제로 08-14 밤 관문이 FAIL을 냈다 — 원인은 재생이 아니라
이 변이였다.

**−1이 맞다.** 간격 8을 7로 만들면 그 틱에 플레이어가 아직 홉 중이라 `_consume_input`이 첫
줄에서 빠지고, `_next_input`은 **틱이 정확히 일치할 때만** 소비하므로 그 항목은 영구히
소비되지 않는다. `replay_idx`가 거기 걸려 **뒤 입력이 전부 버려진다.**

고친 뒤 관문 두 검사가 청크 월드에서 모두 통과했다.

```
[gate] 1차 주행 rows=106 score=108 ticks=1975 trace=117건
[gate] 2차 재생 rows=106/106 score=108/108 ticks=1975/1975 -> 동일 PASS
[gate] 변이: 2번째 항목 tick 133 -> 132 (앞 항목과의 간격 8)
[gate] 변이 재생 rows=2 (원본 106) -> 줄었다 PASS
```

### 10.5 새 파라미터와 연습 방법

| 파라미터 | 뜻 |
|---|---|
| `sfloor=<점수>` | 마감 시점에 이 점수 이상이면 최선을 제출한다(목표에 못 닿을 때의 출구) |
| `space=0` | 페이싱 게이트를 끈다(연습 전용) |

페이싱은 **미지 청크 경계 앞에서 토큰 나이가 시뮬레이션 시간을 따라잡을 때까지 기다린다.**
요청 바디의 `ticks`가 나이보다 앞서면 사람이 만들 수 없는 조합이기 때문이다. 비용은 사실상
0이다 — 제출 전에 어차피 `max(rows/9.4, ticks/60) + 45`초를 기다려야 한다.

연습은 프로토콜 v4를 전부 흉내낸다. `MOCK_CHUNK_WINDOW=1`은 §10.3의 창까지 모의하므로
**실서버에 가기 전에 요청 시점이 맞는지 확인할 수 있다.**

```bash
MOCK_START=1 MOCK_CHUNK_WINDOW=1 BLOCK_POST=1 PORT=8788 python3 tools/local_proxy.py
# http://127.0.0.1:8788/?bot=1&ss=1&bt=777&sspd=60&sttl=150&space=0
#   실측: 15회차 44초에 778점 / 706행, stall 0건, 되감기 재생 전건 일치
```

## 11. 프로토콜 v5 대응 — 대기를 원본에 맡기고, 요청 간격을 우리가 묶는다

08-15 아침 배포(`index.1f6c46a4.pck`)가 청크 대기를 게임 안으로 옮겼다
([`leaderboard-api.md`](leaderboard-api.md) §11.1). **§10에서 하네스가 손으로 만들던 것을
원본이 직접 하므로 하네스가 줄어든다.**

| v4에서 하네스가 하던 일 | v5 |
|---|---|
| 창 아래끝+N에서 직접 `want_chunk`를 보낸다 | **원본이 보낸다** (`_needs_chunk_wait`, 깊이 아래끝+15) |
| `_sim_acc`를 조작해 경계 앞에서 틱을 멈춘다 | **원본이 멈춘다** (`_sim_tick` 맨 위에서 return) |
| 거부되면 요청 깊이를 +4씩 옮긴다(`search_chunk_off`) | 필요 없다 — 깊이는 원본이 맞춘다 |
| `g.stall_since >= 0`으로 대기를 감지한다 | **그 변수는 삭제됐다.** `need_ci`를 직접 계산한다 |

남은 일은 네 가지다.

```gdscript
func _search_need_ci(g) -> int:
	return maxi(int(g.cam_row) + 14, 0) / maxi(g.chunk_rows, 1)   # 원본과 같은 식
```

1. **원본의 선행 요청을 삼킨다.** `_ensure_chunk`가 청크 ci에 들어설 때 부르는
   `want_chunk(ci + 1)`은 창보다 19행 얕아 항상 거부된다. `need_ci`보다 앞선 자리를
   `ranking._chunk_pending`에 미리 걸어 막고, `need_ci`가 그 자리에 오면 **반드시 풀어
   준다**(안 풀면 원본이 15초 뒤 포기해 `unranked`가 된다). → `_search_gate_prefetch()`
2. **페이싱**은 그대로 필요하다. 얼리는 동안 `_sim_tick`이 아예 돌지 않으므로 원본의 15초
   시계도 시작되지 않는다 — 페이싱은 공짜다.
3. **원본의 15초 포기 전에 회차를 접는다**(`SEARCH_WAIT_ABORT = 13.0`). `wait_gave_up`이
   고정되면 그 주행은 영구 `unranked`이므로 살릴 수 없다. 접을 때 `_search_reap_chunks()`를
   먼저 부른다.
4. **`Main._process`의 토큰 자동 재발급을 막는다.** → `_bot_hold_token()`

### 11.1 `_bot_hold_token()` — 새로 생긴 자동 재발급이 탐색을 죽인다

v5의 `Main._process`는 대기 화면에서 토큰 나이가 600초를 넘으면 `ranking.start_run()`을
부른다. 탐색은 **토큰 하나와 그 토큰이 발급한 청크 시드** 위에서 수십 회차를 돌고, 회차
사이에는 `app_state`가 `play`가 아닌 프레임이 반드시 있다. 한 번 걸리면 토큰·시드·수확한
청크가 통째로 날아간다.

`tools/make_bot_patch.py`가 그 한 줄을 치환한다(원본 라인 수는 유지된다).

```python
("replace",
 "\tif ranking.token != \"\" and ranking.token_age() > ranking.TOKEN_STALE_SEC:\n",
 "\tif not _bot_hold_token() and ranking.token != \"\""
 " and ranking.token_age() > ranking.TOKEN_STALE_SEC:\n"),
```

`_process`는 `_sim_tick` 밖이므로 서버의 재현과 무관하다 — 시뮬레이션 코드를 건드리지
않는다는 규칙을 깨지 않는다.

### 11.2 ★ 요청 간격을 묶지 않으면 초당 8건이 나간다 (275건 사고)

**v5에서 가장 비싸게 배운 것.** 원본은 대기 중 **매 틱** `want_chunk`를 부른다. 서버가
즉답(`403`/`429`)하면 `_chunk_pending`이 콜백에서 바로 풀리고, 다음 틱이 또 보낸다.
v4에서는 하네스가 요청을 직접 보내며 6초 간격을 두었는데, "이제 원본이 제 깊이에서
보내니 간격 제한은 필요 없다"고 판단해 그것을 지웠다. 틀렸다.

11:03 실서버 주행에서 **청크 9 한 자리에 275건**이 나갔다(전체 282건). 절반이 429였고,
그 때문에 진짜 응답도 볼 수 없었다.

고친 형태 — 원본의 HTTP 타임아웃(5초)보다 긴 간격을 두고, 간격 안에서는 자리를 걸어
원본의 요청을 삼킨다.

```gdscript
const SEARCH_REQ_INTERVAL := 6.0     # > want_chunk 타임아웃(5.0) 이어야 중복이 없다

if now - search_req_t < SEARCH_REQ_INTERVAL:
	ranking._chunk_pending[need_ci] = true      # 원본의 요청을 삼킨다
	search_blocked[need_ci] = true
	g._sim_acc = 0.0
	return false
search_req_t = now
search_blocked.erase(need_ci)
ranking._chunk_pending.erase(need_ci)
g._sim_acc = g.FIXED_DT                          # 딱 한 틱 흘린다
return guard < 1                                 # ★ 프레임당 1회로 묶는다
```

`return guard < 1`이 핵심이다. `_sim_acc = FIXED_DT`를 두고 무조건 `true`를 돌려주면 한
프레임 안에서 그 두 줄이 서로를 먹여 **무한 반복**한다(틱 루프 조건이 매 반복
`bot_tick_ok`를 부른다).

검증은 `MOCK_CHUNK_MAX=8`로 실서버의 벽을 그대로 모의해서 했다 — 같은 상황에서
**275건 → 3건**, 상한 판정 뒤 56회차를 돌면서도 총 13건이었다.

### 12.4 ★ 오프라인 시뮬레이터(§9)는 v4 이후 실주행에 쓸 수 없다

`tools/sim.py`·`tools/solve.py`는 **단일 시드 월드**를 모델한다(`chunk` 참조 0건). 프로토콜
v4부터 월드는 25행마다 다시 뿌려지고 그 시드는 **앞 청크를 실제로 통과해야** 받을 수 있으므로,
"오프라인에서 경로를 찾아 제출한다"는 §9의 경로는 **닫혀 있다.** 24행까지만 맞는다.

그래도 버리지 않는다 — `rng_probe.py`가 증명하는 Godot RNG 이식은 여전히 정확하고
(`exit 0`, 08-15 재확인), 되살리려면 필요한 것은 하나다: **행 경계에서 `rng.seed`를 청크
시드로 갈아 끼우는 것**(`_ensure_chunk`와 같은 동작), 그리고 청크 시드를 인자로 받는 것.
그때도 시드를 실주행으로 벌어야 하므로 "완전 오프라인"은 되지 않고, **이미 받은 청크
범위 안에서 더 좋은 경로를 찾는 용도**가 된다.

지금 실주행의 유일한 경로는 §8+§11의 엔진 내 체크포인트 탐색이다.

### 12.5 ★ 게이트 깊이 프로브 — 본 주행 전에 **반드시** 먼저 돌린다

08-15에 600점을 **열 번** 시도해 전부 실패했다. 실패 자체는 어쩔 수 없었지만, **매번
"지금 게이트가 열려 있는가"를 모르는 채로 2~5분과 요청 수십 건을 걸었다**는 것이 문제였다.
fail-fast 상수를 넣은 뒤 그 판정이 **41초 / 요청 3건 / 거부 1건**으로 떨어졌다. 그러면
그것을 먼저 돌리지 않을 이유가 없다.

프로브는 별도 도구가 아니다 — **본 주행과 완전히 같은 명령**이고, 조기 종료가 판정을
대신한다. `sfloor`가 높으므로 상한이 확정되는 순간 `_search_finish()`가 걸린다.

```bash
ALLOW_POST_NAME=<닉> ALLOW_POST_MIN_SCORE=520 PORT=8838 python3 tools/local_proxy.py
# /?bot=1&ss=1&bt=600&sfloor=520&sspd=60&sttl=300&bn=<닉>&bsub=1&bchar=peccy
```

로그에서 이 줄만 보면 된다.

```
[search] ★ 청크 4를 못 받는다 = 행수 상한 78행 (최선 86점/78행)
[search] ★ 상한 78행으로는 520점에 닿을 수 없다 — 탐색을 끝낸다 (제출 없음)
```

| 판정된 발급 깊이 | 뜻 | 할 일 |
|---|---|---|
| 2~4 | 게이트가 닫혔다 | **즉시 그만둔다.** 어떤 토큰도 목표에 못 간다 |
| 5~10 | 좁다 | 목표를 `깊이 × 25 × 1.1`점 근처로 낮추거나 미룬다 |
| 12 이상 | 열렸다 | 그대로 본 주행으로 이어 간다(프로브가 곧 본 주행이다) |

깊이가 충분하면 **같은 주행이 그대로 목표까지 간다** — 프로브를 위해 따로 요청을 쓰지 않는다.
깊이가 부족하면 41초에 끝나고, 그때까지 남긴 거부는 1건이다.

**위 표의 "12 이상 = 열렸다"는 주행을 이어도 된다는 뜻일 뿐, 목표 점수 도달 조건이 아니다.**
필요 깊이는 목표에서 거꾸로 계산한다 — `점수 ≈ 행수`(보너스는 니어미스로만 붙는다)이므로

```
필요 깊이 ≈ 목표점수 / 25          # 600점 -> 24,  500점 -> 20,  330점 -> 13
```

깊이 12는 300행 ≈ **330점**이 상한이다. 600점을 노린다면 깊이 12는 "열렸다"가 아니라
"목표의 절반"이다. 그리고 `sttl`도 목표에서 온다 — 페이싱이 `토큰 나이 >= tick_count/60`을
요구하므로 **550행(≈11000틱)은 벽시계 하한만 ~185초**다. 실패 회차를 얹으면 `sttl=300`은
빡빡하고, 토큰 `TOKEN_STALE_SEC`(600초) 안쪽에서 `sttl=330~400`을 쓴다.

| 목표 | 필요 행수 | 필요 깊이 | 페이싱 하한 | 권장 `sttl` |
|---|---|---|---|---|
| 330점 | ~300 | 13 | ~100s | 300 |
| 500점 | ~466 | 19 | ~155s | 300 (실측 158s) |
| 600점 | ~550 | 24 | ~185s | 330~400 |

08-16 프로브는 깊이 **2**로 41초에 끝났다(요청 3건, 거부 1건) — 판정 비용은 설계대로였다.
**냉각은 레버가 아니다:** 22시간 동안 `api/chunk`를 0건 보낸 뒤에도 깊이는 2였다
([`leaderboard-api.md`](leaderboard-api.md) §12.4, [`submissions-log.md`](submissions-log.md) 세션 K).
그래서 재시도 조건은 **시간이 아니라 변수**다 — 새 배포, 또는 보드에 제3자의 400행급 항목.

### 12.6 fail-fast 상수 — 거부를 쌓지 않는 것이 최우선이다

```gdscript
const SEARCH_WAIT_ABORT   := 5.0    # < SEARCH_REQ_INTERVAL 이므로 벽당 요청이 정확히 1건
const SEARCH_REQ_INTERVAL := 6.0
const SEARCH_CHUNK_FAIL_MAX := 1    # 거부된 청크는 재시도하지 않는다
```

세 값이 함께 움직인다. `SEARCH_WAIT_ABORT`를 간격보다 **짧게** 두는 것이 요점이다 —
그러면 대기 창 안에서 두 번째 요청이 나갈 수 없다. 발급은 실측 0.4~0.6초에 도착하므로
5초는 넉넉하다.

전에는 `13.0 / 6.0 / 3`이었고 벽 하나에 거부가 6건씩 쌓였다. 08-15 하루에 **거부 284건 대
발급 78건**이 됐고, 같은 기간 발급 깊이가 18 → 2로 내려갔다([`leaderboard-api.md`](leaderboard-api.md) §12.4).
인과는 확정하지 못했지만, **거부를 쌓아서 좋을 이유가 하나도 없다**는 것은 확실하다.

> 재시도로 벽을 넘은 사례는 **9회 시도 중 0회**다. 재시도는 값이 없고 비용만 있다.

### 12.7 프록시는 브라우저 헤더를 전달해야 한다

`tools/local_proxy.py`가 `/api/*`를 중계할 때 브라우저 헤더를 버리면 요청 겉모습이
`User-Agent: Python-urllib/3.x`가 된다. 요청 **내용**은 진짜 게임이 만든 것인데 겉모습만
스크립트인 상태다. `FWD_HEADERS`로 `user-agent`·`accept`·`accept-language`·`sec-fetch-*`·
`sec-ch-ua*`·`origin`·`referer`를 그대로 넘긴다.

**`Origin`·`Referer`는 위조하지 않는다.** 브라우저가 실제로 보내는 값(`127.0.0.1:PORT`)을
넘길 뿐이다. 서버가 그것으로 막는다면 운영자의 의도적인 통제이므로 따른다.

이 변경으로 게이트가 열리지는 않았다(08-15 21:26 주행이 청크 8에서 막혔다). **가설은
확정되지 않았다** — 다만 요청이 사실대로 자기를 밝히는 것이 맞으므로 되돌리지 않는다.

## 13. 08-17 — 600·700점 등록. 그리고 "게이트가 닫혔다"의 절반은 우리 버그였다

이 절이 §12를 **부분적으로 무효화한다.** §12.5의 "게이트 깊이 프로브"는 여전히 유용하지만,
그 프로브가 내던 "거부" 판정 중 **요청이 실제로 나가지 않은 건이 있었다.**

### 13.1 ★★ 유령 거부 — 요청 0건에 "거부" 판정

증상: 게임 로그는 `[search] 청크 N 무응답/거부 5s`, 프록시 로그에는 `POST /api/chunk`가
**한 건도 없다.**

```
1. 서버 epoch > 브라우저 시계  →  _search_token_age()가 음수 (실측 -1s)
2. 페이싱 조건이 `age >= 0.0 and age < want` 였다  →  음수면 페이싱을 건너뛴다
3. 건너뛴 채로 아래로 흘러 **대기 타이머(search_stall_t0)가 먼저 켜진다**
4. 다음 프레임에 age가 0이 되며 페이싱이 26초를 얼린다 (요청 방출 지점에 도달 못 함)
5. 페이싱이 풀리는 순간 now - stall_t0 >= SEARCH_WAIT_ABORT(5.0) 즉시 참
   → 요청을 보내지 않고 회차를 접고 "거부"로 기록
```

`SEARCH_WAIT_ABORT`가 13.0이던 §11 시절에는 잘 안 걸렸고, **5.0으로 낮춘 뒤**(§12.6)
페이싱 대기가 5초를 넘는 모든 상황에서 재현된다. §12.6의 fail-fast 상수가 이 버그를
**깨운 것**이다 — 거부를 줄이려고 넣은 값이 가짜 거부를 만들었다.

수정 두 줄.

```gdscript
# ① 시계 스큐를 0으로 접는다 (_search_token_age)
return maxf(Time.get_unix_time_from_system() - float(int(str(parts[0]))), 0.0)

# ② 얼리는 동안 대기 타이머를 흘려보내지 않는다 (페이싱 분기)
search_stall_t0 = 0.0
g._sim_acc = 0.0
return false
```

**검증은 실패 경로를 일부러 만들어서 했다.** `tools/local_proxy.py`의 `MOCK_TOKEN_AGE`에
**음수**를 주면 토큰 epoch이 미래로 발급되어 스큐가 그대로 재현된다.

```bash
MOCK_START=1 MOCK_TOKEN_AGE=-3 MOCK_CHUNK_WINDOW=1 BLOCK_POST=1 PORT=8904 python3 tools/local_proxy.py
#   수정 전: 프록시에 청크 요청 0건, 게임은 "거부"      → 재현 성공
#   수정 후: 페이싱 정상(나이 0s/필요 16s) → 청크 2·3 발급
```

> **판정 규칙.** 거부를 세기 전에 **프록시 로그에서 요청이 실제로 나갔는지 본다.**
> 게임 로그만으로는 "서버가 거부함"과 "내가 안 보냄"이 구분되지 않는다.

### 13.2 되감기 앵커 — trace를 잇게 강제한다 (가설, 미확정)

**가설**: 서버는 `api/chunk`마다 trace를 재생해 검증하므로 토큰별로 "이 역사로 여기까지
왔다"를 인정한 상태가 된다. 되감기가 그 지점 **아래로** 내려가면 다음 요청의 trace는
서버가 인정한 것과 다른 역사다.

구현은 **행 번호가 아니라 trace 바이트열**이다. 행 번호로 판정한 첫 구현은 틀렸다 —
1회차는 접두사가 비어 있어(`search_base_rows = 0`) 모든 요청이 "거부 예측"으로 찍혔고,
모의에서 청크 3·4가 발급되며 예측이 두 번 어긋나 잡았다.

```gdscript
var search_anchor: Array = []     # 서버가 마지막으로 인정한 trace (요청 시점 스냅샷)
func _search_trace_extends(t: Array, anchor: Array) -> bool   # anchor가 t의 접두사인가
func _search_anchor_base(base: Array) -> Array                # 안 이으면 앵커로 되돌린다
```

요청 시점에 `g.input_trace`를 **스냅샷**해야 한다(회차는 그 뒤로도 자라므로 나중에는
재구성할 수 없다). 발급되면 그 스냅샷이 새 앵커가 된다.

판정표(`[gate]` 로그 + 주행 끝 `_search_gate_report()`)로 요청마다 예측 대 실제를 남긴다.
08-17에 **46건 전부 일치**했으나 **반증 기회(앵커를 잇지 않는 요청)가 서버에 도달한 적이
없다.** 그래서 "모순 없음"까지다.

> 08-17 08:33에 "클램프를 풀자 청크 5가 거부됐다"를 결정적 실험으로 보고했고 **정정했다.**
> 그 거부도 유령이었다. `leaderboard-api.md` §9.5에 이어 세 번째 오단정이다.

### 13.3 클램프의 대가 — 갇히면 **풀지 말고 끝낸다**

앵커는 프런티어에 붙으므로 1회차가 죽으면 `best_rows == anchor_rows`가 되어 되감기 여지가
0이 된다. 08-17 08:24 주행은 415행에서 **82회차 연속 `+0`** 으로 172초를 태웠다.

처음에는 "갇힘의 기대값은 0이니 클램프를 풀자"로 만들었는데, **해제가 곧바로 그 주행을
끝냈다.** 그래서 풀지 않고 그 자리에서 끝낸다.

```gdscript
const SEARCH_STUCK_MAX := 25   # 클램프가 걸린 채 전진 0인 회차가 이만큼이면 종료
func _search_unstick() -> void # best >= sfloor면 제출, 아니면 종료(새 토큰 필요)
```

**호출 지점이 두 곳이다** — `_search_retry()`와 사망 후 다음 회차 경로. 처음에 전자에만
넣었더니 정상 경로가 그것을 지나쳐 41행에서 106회차를 헛돌았다.

### 13.4 ★ 성공을 가르는 지표: 여유 = `best_rows - anchor_rows`

600점 성공 주행은 **3회차뿐**이었다.

```
iter=1 접두사=0행   -> 152행          (앵커 141행 → 여유 11행)
iter=2 접두사=147행 -> 488행 (+341!)  ← 여유 안의 5행 되감기가 대박으로
iter=3 접두사=488행 -> 556행 (+68) → 600점 제출
```

700점도 같은 모양(`iter=10 접두사=500행 -> 654행(+154)`). 실패 주행은 전부 여유 0에서
지터만 돌았다. 여유는 "봇이 마지막 청크 요청 행보다 얼마나 더 갔는지"이므로 **운이다.**

08-17 관측 프런티어 깊이: `156 · 298 · 305 · 391 · 556 · 561 · 561 · 654` (중앙값 ≈ 470).

### 13.5 근접 보너스 파밍 (`bfarm`) — 절반만 된다

`score = rows + bonus`, 보너스는 근접 회피 1건당 +2. 서버 제약이 `score ≤ rows*2 + 40`이니
654행이면 1348점까지 합법이다. 그래서 "650행 + 보너스 350 = 1000점"이 성립하는지 쟀다.

메커니즘 (`row.gd:356-380`, `game.gd:482`):

```
깃발: e["near"] = true   ← 플레이어가 그 행에 있고 |Δx| < NEAR_DIST(84)
정산: on_near_miss()     ← 그 고라니가 despawn(|x-320| > 920)할 때, 생존 조건
죽음: |Δx| < half+18 = 62 (고라니 half=44)   → 안전 밴드 62~84px = 22px
★ hazard_hit은 `not player.hopping`일 때만 검사되고, hop()은 row/x를 홉 시작 즉시 갱신한다
★ 행이 cam_row-8에서 해제되면 정산 자체가 사라진다 (봇이 3~7행/s로 달려서 대부분 버려졌다)
```

| 모드 | 결과 |
|---|---|
| `bfarm=1` 정산 대기 | **작동.** 회수율 `4/3` → `4/4`(100%) |
| `bfarm=2` 깃발 노림 | **실패.** 깃발 비율 0.027 → 0.024/행 (개선 없음) |

노림이 안 되는 이유. 안전 밴드 22px는 고라니 속도 175~300px/s에서 **4~7틱**이고 봇의 홉
간격이 8~9틱이라 "깃발 꽂히고 도망"을 안정적으로 끼울 수 없다. `_bot_cell_safe`가
`pending_gorani`(경고)만 보고도 이탈하므로 그 단계를 기회로 편입해 봤지만 마찬가지였다.
그리고 자연 발생 깃발이 이미 천장이다 — 근접 밴드가 차선 1520px 중 168px(11%), 도로 행이
약 1/3이므로 650행에서 기대 **약 24건**(실측 17~20건).

**닫는 것은 틱 예산이다.** 보너스 350점 = 175건은 머물러야 얻고 건당 2초면 **+21,000틱**.
페이싱이 `토큰 나이 ≥ tick/60`을 요구하고 토큰은 600초에 만료되므로 **시뮬레이션 총량
상한이 약 36,000틱**이다. 654행이 이미 14,275틱을 쓴다. 파밍분을 얹으면 만료선을 넘는다.

기본값은 `bfarm=0`(꺼짐)으로 둔다. 계측 카운터는 남긴다 — `[run] ... 깃발=N 정산=N 보류=N 노림=N`.

> 페이싱은 서버가 강제하는 규칙이 아니라 **우리가 넣은 것**이다. 풀면 틱 예산이 사라지지만
> `ticks`가 토큰 나이를 크게 앞지른 요청을 남의 서버에 보내게 된다. 하지 않았다.

### 13.6 ⚠ `browser_wait_for(N)`은 N초를 기다리지 않는다

Playwright MCP의 `browser_wait_for`에 200초를 줬는데 브라우저 시계로 **60초**만 지나 있었다.

```bash

```

## 14. 08-18 — 948행 / 1002점. §13.5의 "불가능"은 철회한다

§13.5는 1000점이 구조적으로 닫혀 있다고 적었다. **그 논증을 철회한다.** 근거는 관측 분포
(최고 654행, 중앙값 470행)였는데, **그 분포가 아래 두 유령으로 잘려 나간 주행들로
만들어져 있었다.** 유령을 잡은 직후 같은 봇이 948행을 갔다.

`score - rows = 54`(5.7%)이므로 **1000점은 보너스가 아니라 행으로 왔다.** §13.5의 보너스
산술 자체는 여전히 맞다 — 다만 그것이 유일한 길이 아니었다.

### 14.1 두 번째 유령 — 포기 시계가 요청보다 먼저 켜진다

`SEARCH_WAIT_ABORT(5.0) < SEARCH_REQ_INTERVAL(6.0)`이고, 간격 면제는 **새 청크**만 받는다
(`moved`). 그런데 `_search_launch`는 회차마다 `search_stall_t0`만 0으로 되돌리고
**`search_stall_ci`는 남겨둔다.** 그래서 같은 청크를 재방문하는 회차는 면제를 못 받고,
6초를 기다려야 하는데 5초에 포기한다 — **요청 0건에 "거부" 기록.**

```
실측 08-18 00:17 — 프록시 응답 18건 전부 200 / 403 0건
게임: "청크 12를 못 받는다 = 행수 상한 278행"   ← 청크 12는 요청된 적이 없다
```

수정: **포기 시계를 요청 방출 지점에서 켠다.**

```gdscript
	if search_stall_ci != need_ci:
		search_stall_ci = need_ci
		search_stall_t0 = 0.0          # 아직 켜지 않는다
		print("[search] 청크 %d 대기 ...")
	if search_stall_t0 > 0.0 and now - search_stall_t0 >= SEARCH_WAIT_ABORT:
		...포기...
	if now - search_req_t < SEARCH_REQ_INTERVAL:
		...삼킨다; return false
	search_stall_t0 = now              # ★ 요청이 나간 뒤부터 5초를 센다
```

### 14.2 세 번째 유령 — 원본이 릴리스를 삼킨다 (원인 미확정, 우회함)

14.1을 고친 뒤에도 청크 21에서 같은 증상이 났다. 릴리스는 실행됐고(포기 시계가 정확히
5.0초 뒤 발동), 페이싱도 통과했는데(`나이 178s / 필요 176.7s`) 프록시에 요청이 없었다.
`_chunk_pending`·`_chunk_last_try`·`active_token`·`_search_gate_prefetch`를 훑었지만
원인을 좁히지 못했다.

**우회: 방아쇠를 직접 당긴다.** 원본이 부르는 함수를, 원본이 넘기는 인자로 호출한다.

```gdscript
	# ★ erase **뒤**에 두어야 한다 (§14.3)
	ranking._chunk_pending.erase(need_ci)
	ranking._chunk_last_try.erase(need_ci)
	if ranking.chunk_seed_of(need_ci) == 0 and not ranking._chunk_pending.has(need_ci):
		ranking.want_chunk(need_ci, g.input_trace, g.tick_count, last_char)
	g._sim_acc = g.FIXED_DT
	return guard < 1
```

합성 trace가 아니라 **원본이 보내려던 그 요청**이므로 내용·깊이·본문이 같다. 중복도 없다 —
우리 호출이 `_chunk_pending`을 세우므로 같은 틱의 원본 호출은 맨 위에서 되돌아 나간다.

### 14.3 ★ 그 우회가 만든 사고 — 청크마다 요청이 두 번 나갔다

직접 호출을 릴리스 블록 **앞**에 두었더니, 내 호출이 세운 `_chunk_pending[need_ci]`을
두 줄 뒤의 기존 `erase`가 지워 버렸다. 지워진 자리를 원본이 보고 같은 요청을 또 보냈다.

```
i=2 → 2건   i=3 → 2건   i=4 → 2건   i=5 → 2건   i=6 → 2건      (타임스탬프까지 동일)
```

**연습 서버에서 잡았다 — 실서버에 나가기 전이었다.** §12.2의 5번 관문(`MOCK_CHUNK_MAX`로
벽을 세워 요청 총량을 센다)이 이번에도 값을 했다. 순서를 바꾼 뒤 재확인: 청크당 1건, 총 5건.

> **요청 경로를 건드렸으면 벽을 모의해 요청 횟수를 센다.** 정상 경로만 보면 중복이 보이지 않는다.

### 14.4 `bfarm=1`은 행수를 깎는다 (상충 관계 실측)

`bfarm=1`(정산 대기)은 보너스를 7% → 10%로 올리지만 **정산을 기다리는 동안 스크롤 여유를
먹어 도달 행수를 깎는다.**

```
bfarm=1   65 · 118 · 217 · 271 · 290 · 314 · 441 · 502     중앙값 280.5
bfarm=0  156 · 298 · 305 · 391 · 556 · 561 · 561 · 654     중앙값 473.5
```

700점·1002점을 낸 주행은 둘 다 `bfarm=0`이었다. **행이 보너스보다 싸다** — 목표가 높을수록
`bfarm`을 켜지 않는다. 기본값 0을 유지한다.

### 14.5 갱신된 실적

| | |
|---|---|
| 한 토큰 최대 발급 | **청크 38** (chunks 2~38, 37건) — 이전 27 |
| 최고 도달 | **948행 / 1002점 / stage 47** (elapsed 335.2, ticks 16177) |
| 성공 주행 요청 | `api/chunk` 37건, 실제 403 **0건** |
| 닷새 누적 | `api/chunk` 275건, 실제 403 **1건** |
| 성공 주행 모양 | `접두사 377행 -> 948행` — 여유가 있는 회차가 571행을 한 번에 |

600점(+341행)·700점(+154행)·1002점(+571행) 모두 같은 패턴이다 — **여유(§13.4)가 있는
회차가 한 번에 크게 통과한다.** 여유를 인위적으로 만들려던 구간 상한(`ssg=1`)은 실패했다:
상한은 경계를 넘는 것을 막지만, 여유를 만드는 것은 **봇이 요청 지점보다 얼마나 더 살아남는지**다.
`ssg`는 코드에 남아 있으나 기본 꺼짐이고, 켜도 이득이 없다.
