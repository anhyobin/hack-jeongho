# 리더보드 API와 서버 측 검증 규칙

`GAME_STRUCTURE.md` §7.2는 **클라이언트가 보내는 것**까지를 다룬다. 이 문서는 그 다음 —
**서버가 무엇을 거부하는가** — 를 실측으로 채운 것이다. 서버 소스는 확보하지 못했으므로
모든 규칙은 요청/응답 관측에서 유도했고, 확정된 것과 추정을 구분해 적었다.

## 1. 계약 요약

베이스 URL은 `Ranking.base_url()`이 페이지 URL에서 유도한다(항상 same-origin, CORS 없음).

| 엔드포인트 | 메서드 | 바디 | 응답 |
|---|---|---|---|
| `api/start` | GET | — | `{"token": "<epoch10>.<hex16>.<hex16>"}` |
| `api/scores[?char=<id>]` | GET | — | `{"scores": [...]}` — 상위 50개, score 내림차순 |
| `api/scores` | POST | `{name, score, rows, char, token}` | `{"ok": true, "rank": N, "scores": [...]}` |

토큰 앞부분 10자리는 발급 시각 epoch이고 응답의 `date` 헤더와 일치한다.
뒤의 hex 16+16은 nonce와 서명으로 보인다(추정 — 서버 코드 없음).

POST 성공 응답의 `scores` 엔트리에는 GET에는 없는 **`rows` 키가 포함된다**. 즉 서버는
`rows`를 그대로 저장하며, `stage`는 `rows`에서 파생시킨다.

파생식은 **`floor(rows/20)`** 이다 — `+1`이 붙지 않는다. `rows`가 남아 있는 항목 7건이 예외 없이 일치한다.

| rows | 3000 | 2000 | 1580 | 1500 | 1004 | 990 | 220 |
|---|---|---|---|---|---|---|---|
| 저장된 stage | 150 | 100 | 79 | 75 | 50 | 49 | 11 |

즉 서버는 `ThemeDefs.stage_index()`(0-기반)를 그대로 저장한다. 게임 화면의 `STAGE %d` 배너가
`s_idx + 1`로 1-기반 표시를 하는 것(game.gd `_apply_stage_visuals`)과 혼동하지 않아야 한다.
`rows` 키가 없는 옛 항목(예: `민지 401 / stage 16`)은 서버가 `rows`를 저장하기 전에 기록된 것으로,
정합성 검사(§2 `inconsistent`)가 나중에 추가된 방어라는 정황이다.

### `admin_insert` — API를 우회하는 경로가 있다

2026-08-13에 관측된 `호호호 2500 / rows 2480` 항목에는 **클라이언트가 보내지 않는 키
`"admin_insert": true`** 가 붙어 있다. `ranking.gd`가 보내는 필드는 `name/score/rows/char/token`
뿐이므로(§5), 이 키는 서버 운영자가 POST 검증을 거치지 않고 항목을 직접 넣을 수단을 갖고 있고
그렇게 넣은 항목을 표시해 둔다는 뜻이다. 같은 닉네임의 `2501 / rows 2495`에는 플래그가 없어
정상 POST 경로로 올라왔다. 따라서 **보드의 항목은 두 출처가 섞여 있고**, 이 플래그가 유일한 구분자다.
검증 규칙을 논할 때 `admin_insert` 항목은 표본에서 제외해야 한다 — 어떤 검사도 통과하지 않았다.

## 2. 거부 응답 4종 — 구분이 중요하다

| 응답 | 의미 | 보드에 항목이 남는가 |
|---|---|---|
| `403 {"ok": false, "error": "too_fast"}` | **점수 검증 실패.** 토큰 나이에 비해 `score`가 과도함 | 아니오 |
| `403 {"ok": false, "error": "inconsistent"}` | **정합성 실패.** `score > rows * 2` | 아니오 |
| `{"ok": false, "error": "token:reused"}` | **토큰 소진.** 이미 한 번 처리된 토큰 | 아니오 |
| `429 {"ok": false, "error": "too fast"}` | **IP 레이트리밋.** 밑줄이 아니라 **공백**인 점에 주의 | 아니오 |

`too_fast`(밑줄, 403)와 `too fast`(공백, 429)는 완전히 다른 원인이다. 이걸 혼동하면
"점수가 너무 높아서 막혔다"고 오판하게 된다 — 실제로는 동시 요청 때문에 IP 스로틀에 걸린 것이다.
POST 3개를 동시에 던졌을 때 2개가 429를 받았으므로, **제출은 최소 60초 간격으로 직렬화**한다.

### 검사 순서 — 스로틀이 가장 먼저다

**존재하지 않는 토큰, 그리고 `token` 필드를 아예 뺀 요청도 `too fast`(공백)를 받는다.**
따라서 IP 스로틀은 토큰 검증보다 **앞에** 있다. 관측된 순서는 다음과 같다.

```
IP 스로틀(429 too fast) → 토큰 검증(token:reused) → 정합성(403 inconsistent) → 속도(403 too_fast)
```

실무적 함의: 프로브를 몰아서 던지면 **아무 정보도 얻지 못한다.** 같은 토큰으로 6번 연속 던졌을 때
첫 요청만 실제 검사까지 도달해 `too_fast`를 받고, 나머지 5개는 전부 `too fast`였다.
30초 이상 간격을 두지 않으면 응답이 검사 결과가 아니라 스로틀 결과다.

### 토큰은 1회용이고, 거부된 시도에도 소모된다

30초 쉬고 같은 토큰을 다시 쓰면 `token:reused`가 돌아온다. 앞선 시도가 **속도 검증에서 거부**됐어도
토큰은 이미 소진된 상태다. 즉 **토큰 1개 = 시도 1회**이며, "일단 던져보고 실패하면 같은 토큰으로 재시도"는
불가능하다. §4의 스케줄러가 토큰을 여러 개 미리 발급해 두는 설계는 이 성질 때문에 필수다.

거부는 보드에 아무것도 남기지 않는다. 이 성질이 탐색 전략을 결정한다(§4).

## 3. 통과/거부 경계 실측

기본적으로 `score == rows`(보너스 0)로 고정해 정합성 변수를 제거하고, 토큰 나이만 바꿔가며 관측한 결과다.
`rows`를 따로 적은 행은 `score != rows`로 보낸 요청이며, 정합성 검사를 통과한 것들이다(§3 후반 참조).

| 토큰 나이 | score | 비율 | 결과 |
|---|---|---|---|
| ~10s | 10000 (rows 9950) | 1000/s | `403 too_fast` |
| 18s | 10000 (rows 9900) | 555/s | `403 too_fast` |
| 12.3s | 120 | 9.75/s | `403 too_fast` |
| **12.5s** | **100** | **8.00/s** | **`200 ok` (rank 98)** |
| 15s | 60 | 4.00/s | `200 ok` (rank 138) |
| **150s** | **1004** | **6.69/s** | **`200 ok` (rank 2)** |
| 231s | 440 (rows 220) | 1.90/s | `200 ok` (rank 1) |
| 270s | 1004 (rows 990) | 3.72/s | `200 ok` |
| 311s | 1500 | 4.82/s | `200 ok` (rank 1) |
| 381s | 1600 (rows 1580) | 4.20/s | `200 ok` (rank 2) |
| 430s | 2000 | 4.65/s | `200 ok` (rank 1) |
| **480s** (실제 490s) | **3000** | **6.25/s** (실제 6.12/s) | **`200 ok` (rank 1)** |
| 15s | score 100 / **rows 10** | — | `403 inconsistent` |
| 91s | score 10000 / **rows 60** | — | `403 inconsistent` |
| 150s | score 10000 / **rows 150** | — | `403 inconsistent` |

### 규칙의 형태

단순 비율(`score <= elapsed * r`)인지 유예 항이 붙은 형태(`score <= (elapsed + g) * r`)인지는
짧은 프로브만으로는 구분되지 않는다. 다만 두 데이터점이 `g`를 강하게 제한한다.

```
1004 <= (150 + g) * r      (통과)
 120 >  (12.3 + g) * r     (거부)
→ 1004 / (150+g) < 120 / (12.3+g)
→ 884g < 5651  →  g < 6.4초
```

따라서 **유예 항은 6.4초 미만이고, 규칙은 사실상 단순 비율에 가깝다.**
허용 비율 `r`은 **6.4 ~ 9.75 점/초** 구간이다(8.00/s 통과, 9.75/s 거부).

`r`의 하한 6.4/s를 안전값으로 쓰는 방식은 실제로 검증됐다. 2026-08-13에 **3000점을
토큰 나이 480초(스케줄값)에 첫 시도로 통과**시켰다 — 6.4/s 하한이 요구하는 469초에
11초만 얹은 값이다. 큰 점수에서도 규칙이 비율 하나로 설명된다는 근거다.

**단, 이 480초는 나이의 하한값이다.** `submit_target.py`는 토큰을 5초 간격으로 전부 발급한
뒤 마지막 발급 시점을 `t0`으로 잡으므로, 먼저 발급된 토큰은 스케줄값보다 오래 묵는다.
실제로 쓴 토큰은 `t0`보다 10초 앞서 발급된 0번이었고 **진짜 나이는 490초, 진짜 비율은 6.12/s**다.
즉 이 데이터점이 확정하는 것은 `r >= 6.12`(로그의 6.25가 아니다)와 `TTL >= 490초`다.
로그의 나이/비율은 항상 보수적인 쪽(나이 과소·비율 과대)으로 어긋나므로,
통과를 근거로 `r`의 하한을 말할 때는 반드시 실제 발급 시각으로 되짚어야 한다.

게임의 실제 최대 이동 속도(홉 0.13초 → 약 7.7행/초)가 이 구간 안에 들어온다는 점에서,
서버는 "물리적으로 가능한 최대 전진 속도"를 상한으로 잡았을 가능성이 높다(추정).

`score`와 `rows`가 다른 요청들도 모두 비율 조건에 걸리지 않았다(3.72/s, 4.20/s 통과).
`rows`가 아니라 `score`를 기준으로 본다고 단정할 수는 없지만, 두 값이 근접한 제출만 통과시켰으므로
어느 쪽을 쓰든 결과는 같다. 안전하게는 **두 값 모두** 비율 조건을 만족시키는 게 맞다.

### 정합성 규칙의 형태

`score`와 `rows`의 허용 괴리는 **`score <= rows * 2`** 로 보인다.

| score / rows | 비율 | 결과 |
|---|---|---|
| 440 / 220 | **정확히 2.0배** | `200 ok` — 경계 통과 |
| 1600 / 1580 | 1.01배 | `200 ok` |
| 100 / 10 | 10배 | `403 inconsistent` |
| 10000 / 150 | 66.7배 | `403 inconsistent` |
| 10000 / 60 | 167배 | `403 inconsistent` |

확정된 것은 **2.0배가 통과하고 10배는 거부된다**는 것이고, 임계값은 그 사이다.
2.0이라는 값은 게임 로직과 정확히 맞물린다 — 보너스는 니어미스 1회당 `+2`이고
니어미스는 플레이어가 그 행에 있는 동안에만 판정되므로, 현실적 상한이 행당 `+2`다
(`row.gd` `_step_entities`, `NEAR_DIST = 84`). 즉 서버는 `score - rows <= rows`를
검사하는 것으로 보인다(추정).

실무적으로는 `score == rows`가 가장 안전하고, 보너스를 섞고 싶으면 `rows`를 `score`의 절반 이상으로 두면 된다.
"칸수는 적은데 보너스로 점수만 부풀리기"는 이 검사에 막힌다.

### 목표 점수별 필요 대기 시간

`r`의 하한 6.4/s를 쓰면 안전하다.

| 목표 점수 | 최소 대기(9.75/s 가정) | 안전 대기(6.4/s 가정) | 실측 |
|---|---|---|---|
| 1,004 | 103초 | 157초 | 150초 통과 |
| 2,000 | 205초 | 313초 | 430초 통과 |
| 3,000 | 308초 | 469초 | **480초 통과** (실제 490초) |
| 10,000 | 1,026초 (17분) | 1,563초 (26분) | 미시도 |

## 4. 그래서 어떻게 탐색하는가

거부는 흔적을 남기지 않고, **토큰은 세션에 묶여 있지 않다** — `GET api/start`는 인증이 없고,
여러 개를 미리 받아 병렬로 숙성시킬 수 있다. 이 두 성질을 합치면:

> 토큰을 미리 대량 발급해 두고, **목표 점수를 고정한 채 토큰 나이를 늘려가며 재시도**한다.
> 실패는 비용이 0이고, 첫 성공이 곧 목표 달성이다.

중간 점수로 경계를 이진 탐색하면 성공할 때마다 보드에 쓰레기 항목이 남는다. 목표 점수 자체로
탐색하면 그 문제가 사라진다.

| 스크립트 | 용도 |
|---|---|
| `tools/submit_target.py <score> <name> [char] [ages] [rows]` | 목표 1개를 나이 스케줄대로 재시도. 기본 `480,600,720`초. 3000점을 이걸로 등록했다 |
| `tools/submit_run.py` | 08-12 세션의 2단(1004 → 10000) 스케줄러. 상수가 하드코딩되어 있고 기록용으로 남겨 둔다 |
| `tools/board_probe.py <대기초> <score> [rows] [name] [char]` | 단발 프로브 |

### 검증 관련 실무 주의

- **`score == rows`로 보내라.** 가장 안전하다. 허용 폭은 `score <= rows * 2`로 확인됐으므로(§3) `rows`를 `score`의 절반 이상으로 두면 보너스를 섞어도 통과한다 — 실제로 `440 / rows 220`(정확히 2배)이 통과했다. 반대로 `rows`만 낮춰 점수를 부풀리는 건 막힌다.
- **재시도에는 매번 새 토큰이 필요하다.** 거부된 시도도 토큰을 소진시킨다(§2). 스케줄러가 토큰을 미리 여러 개 발급해 두는 이유다.
- **토큰 나이 측정은 로컬 시계로 하지 마라.** 서버 epoch이 로컬보다 약 2초 앞서 있었다. `now_local - token_ts`로 계산하면 나이를 과소평가한다. 토큰 수신 시각을 `time.monotonic()`으로 잡고 **경과 시간**을 재는 게 맞다(시계 오차가 상쇄된다).
- **TTL 하한은 490초.** 490초 된 토큰이 정상 통과했다(스케줄값 480초 + 발급 간격 10초). 그보다 오래 묵힌 토큰(10000점에 필요한 26분 이상)이 여전히 유효한지는 여전히 미확인이다. 만료가 있다면 `too_fast`가 아닌 다른 에러가 돌아올 것이므로, 스케줄러는 예상 외 에러에서 즉시 중단하도록 되어 있다.
- **점수 상한은 3000까지 없다.** 3000점이 비율 조건만으로 통과했으므로 그 아래에 절대 상한이나 stage 상한은 없다. 10000점은 아직 미확인이다.

## 5. 정적 분석에서 이미 알던 것 (재확인)

- `token`을 제외한 **모든 필드는 클라이언트가 만든 값**이다. `name`은 길이·문자셋 검사가 UI(`max_length=12`)에만 있어 임의 닉네임 사칭이 가능하다 — 실제로 여러 사람이 `핵정호`, `바이브정호` 등으로 등록되어 있다.
- `char`도 임의 문자열이 들어간다. 화이트리스트 검사는 **읽는 쪽**(ui.gd:467)에서만 한다.
- `?s=N`(스테이지 스킵)은 `start_row`가 점수에서 차감되므로 **점수 부풀리기에 쓸 수 없다**.
- 로컬 `user://save.json`의 `best`는 서버로 전송되지 않으므로 리더보드와 무관하다.
- **삭제 엔드포인트가 없다.** 한 번 등록된 점수는 회수할 수 없다.
