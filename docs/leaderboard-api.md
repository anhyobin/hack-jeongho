## 1. 계약 요약

베이스 URL은 `Ranking.base_url()`이 페이지 URL에서 유도한다(항상 same-origin, CORS 없음).

| 엔드포인트 | 메서드 | 바디 | 응답 |
|---|---|---|---|
| `api/start` | GET | — | `{"token": "<epoch10>.<hex16>.<hex16>"}` — 08-14부터 `"seed": "<16자리>"`가 추가됐다(§6) |
| `api/scores[?char=<id>]` | GET | — | `{"scores": [...]}` — 상위 50개, score 내림차순 |
| `api/scores` | POST | `{name, score, rows, char, token}` | `{"ok": true, "rank": N, "scores": [...]}` |

토큰 앞부분 10자리는 발급 시각 epoch이고 응답의 `date` 헤더와 일치한다.
뒤의 hex 16+16은 nonce와 서명으로 보인다(추정 — 서버 코드 없음).

POST 성공 응답의 `scores` 엔트리에는 GET에는 없는 **`rows` 키가 포함된다**. 즉 서버는
`rows`를 그대로 저장하며, `stage`는 `rows`에서 파생시킨다.

파생식은 **`floor(rows/20)`** 이다 — `+1`이 붙지 않는다. `rows`가 남아 있는 항목 7건이 예외 없이 일치한다.

| rows | 3000 | 2000 | 1580 | 1500 | 1004 | 990 | 220 |
|---|---|---|---|---|---|---|---|
| 저장된 stage | 150 | 100 | 79 | 75 | 50 | 49 | 11 |

즉 서버는 `ThemeDefs.stage_index()`(0-기반)를 그대로 저장한다. 게임 화면의 `STAGE %d` 배너가
`s_idx + 1`로 1-기반 표시를 하는 것(game.gd `_apply_stage_visuals`)과 혼동하지 않아야 한다.
`rows` 키가 없는 옛 항목(예: `민지 401 / stage 16`)은 서버가 `rows`를 저장하기 전에 기록된 것으로,
정합성 검사(§2 `inconsistent`)가 나중에 추가된 방어라는 정황이다.

### `admin_insert` — API를 우회하는 경로가 있다

2026-08-13에 관측된 `호호호 2500 / rows 2480` 항목에는 **클라이언트가 보내지 않는 키
`"admin_insert": true`** 가 붙어 있다. `ranking.gd`가 보내는 필드는 `name/score/rows/char/token`
뿐이므로(§5), 이 키는 서버 운영자가 POST 검증을 거치지 않고 항목을 직접 넣을 수단을 갖고 있고
그렇게 넣은 항목을 표시해 둔다는 뜻이다. 같은 닉네임의 `2501 / rows 2495`에는 플래그가 없어
정상 POST 경로로 올라왔다. 따라서 **보드의 항목은 두 출처가 섞여 있고**, 이 플래그가 유일한 구분자다.
검증 규칙을 논할 때 `admin_insert` 항목은 표본에서 제외해야 한다 — 어떤 검사도 통과하지 않았다.

### `elapsed` — 서버가 잰 토큰 나이를 되돌려준다 (08-13 신설)

08-13 13:13에 등록한 항목에는 **`"elapsed": 565.6`** 이 붙어 있다. 같은 날 01:06에 등록한
`정호야호 3000`에는 없다. 즉 이 키는 **그 사이에 추가됐다** — 서버가 실시간으로 수정되고 있다는
직접적인 증거다. 값은 서버가 토큰 발급 시각부터 POST 처리까지 직접 잰 초 단위 경과 시간이고,
우리가 `time.monotonic()`으로 잰 565.6초와 일치했다.

경계 측정에는 이게 로컬 측정보다 낫다 — 서버가 판정에 쓴 값 자체이므로 시계 오차·왕복 지연이
끼어들지 않는다. **속도 규칙을 다룰 때는 `elapsed`를 정본으로 쓴다.**
운영자 입장에서 보면 부정 제출을 사후에 판별하려고 심은 필드로 읽힌다(추정).

### `GET api/scores` 한 번은 보드 상태의 증거가 못 된다

08-13 13:14~13:16 사이 약 2분간, 이 엔드포인트는 **전체 목록에서 상위 11개를 건너뛴 창**
(`scores[11:61]`에 해당)을 돌려줬다. 640점 초과 항목이 정확히 11개였기 때문에, 겉보기로는
"운영자가 640점 넘는 항목을 전부 삭제했다"와 완벽히 똑같이 보였다. 실제로는 아무것도 지워지지
않았고 2분 뒤 원상복구됐다.

구분하는 방법은 하나다 — **저장된 스냅샷과 레코드 단위로 비교**한다.

```
filtered[0:39] == full[11:50]   →  True  (name/score/rows/ts 전부 일치)
```

겹치는 39개가 오프셋만 두고 전부 일치하면 삭제가 아니다. 바깥에서 "상위 11개를 지웠다가
복원했다"와 "창이 밀렸다"를 완전히 구분할 수는 없지만, 우리 항목이 `elapsed`까지 그대로
살아 돌아온 것을 보면 데이터가 유실된 적은 없다. 두 상태의 원본은
`snapshots/board-after-10001.json`(정상)과 `snapshots/board-window-anomaly-1315.json`(이상)에 있다.

**실무 규칙: 한 번의 GET으로 "지워졌다"고 판단하고 재등록하지 마라.** 재폴링이 먼저다.
그렇게 하지 않았다면 이미 1위인 상태에서 불필요한 POST를 한 건 더 남겼을 것이다.

## 2. 거부 응답 4종 — 구분이 중요하다

| 응답 | 의미 | 보드에 항목이 남는가 |
|---|---|---|
| `403 {"ok": false, "error": "too_fast"}` | **속도 검증 실패.** 토큰 나이에 비해 **`rows`**가 과도함 (`rows > elapsed * 9`, §3). `score`는 보지 않는다 | 아니오 |
| `403 {"ok": false, "error": "inconsistent"}` | **정합성 실패.** `score > rows * 2 + 40` | 아니오 |
| `{"ok": false, "error": "token:reused"}` | **토큰 소진.** 이미 한 번 처리된 토큰 | 아니오 |
| `429 {"ok": false, "error": "too fast"}` | **IP 레이트리밋.** 밑줄이 아니라 **공백**인 점에 주의 | 아니오 |

`too_fast`(밑줄, 403)와 `too fast`(공백, 429)는 완전히 다른 원인이다. 이걸 혼동하면
"점수가 너무 높아서 막혔다"고 오판하게 된다 — 실제로는 동시 요청 때문에 IP 스로틀에 걸린 것이다.
POST 3개를 동시에 던졌을 때 2개가 429를 받았으므로, **제출은 최소 60초 간격으로 직렬화**한다.

### 검사 순서 — 스로틀이 가장 먼저다

**존재하지 않는 토큰, 그리고 `token` 필드를 아예 뺀 요청도 `too fast`(공백)를 받는다.**
따라서 IP 스로틀은 토큰 검증보다 **앞에** 있다. 관측된 순서는 다음과 같다.

```
IP 스로틀(429 too fast) → 토큰 검증(token:reused) → 정합성(403 inconsistent) → 속도(403 too_fast)
```

실무적 함의: 프로브를 몰아서 던지면 **아무 정보도 얻지 못한다.** 같은 토큰으로 6번 연속 던졌을 때
첫 요청만 실제 검사까지 도달해 `too_fast`를 받고, 나머지 5개는 전부 `too fast`였다.
30초 이상 간격을 두지 않으면 응답이 검사 결과가 아니라 스로틀 결과다.

### 토큰은 1회용이고, 거부된 시도에도 소모된다

30초 쉬고 같은 토큰을 다시 쓰면 `token:reused`가 돌아온다. 앞선 시도가 **속도 검증에서 거부**됐어도
토큰은 이미 소진된 상태다. 즉 **토큰 1개 = 시도 1회**이며, "일단 던져보고 실패하면 같은 토큰으로 재시도"는
불가능하다. §4의 스케줄러가 토큰을 여러 개 미리 발급해 두는 설계는 이 성질 때문에 필수다.

거부는 보드에 아무것도 남기지 않는다. 이 성질이 탐색 전략을 결정한다(§4).

우리가 도달하지 못한 큰 `rows` 구간을 채워 준다. 이 두 행이 `r`의 하한을 8.84에서 9.487로 올렸다.

### 어느 필드를 보는가 — `score`가 아니라 `rows`다

이 질문은 08-12에는 답할 수 없었다. 그때 보낸 제출은 전부 `score ≈ rows`여서 두 열의
비율이 사실상 같았기 때문이다. **`score / rows`가 2배로 벌어진 제출 하나가 이걸 끝냈다.**

```
score 기준: 통과 최대 17.68/s  vs  거부 최소 9.76/s   → 모순. score 기준일 수 없다
rows  기준: 통과 최대  8.84/s  vs  거부 최소 9.76/s   → r ∈ [8.84, 9.76)
```

`score` 기준이라면 17.68/s를 통과시킨 서버가 9.76/s를 거부했어야 하므로 **논리적으로 불가능하다.**
따라서 **`403 too_fast`는 `rows`를 검사한다.** 08-12 문서가 "score 기준"으로 적었던 것은
표본이 두 가설을 구분하지 못한 결과이며, 이 표의 마지막 통과 행이 그걸 정정한다.

유예 항 `g`도 같은 두 점으로 훨씬 좁게 묶인다.

```
5001 <= (565.6 + g) * r    (통과)
 120 >  (12.3  + g) * r    (거부)
→ 5001 * (12.3+g) < 120 * (565.6+g)
→ 4881g < 6359.7  →  g < 1.30초
```

즉 08-12에 `g < 6.4초`로 잡았던 것이 **`g < 1.3초`로 좁혀졌고, 규칙은 사실상 순수 비율이다.**

### `r`은 9.5다 — `r = 9`는 남의 항목이 반증했다

이 값은 두 번 좁혀졌다. 처음에는 우리 데이터 13건만으로 `[8.84, 9.76)`을 얻고 그 안의
깔끔한 값 `9`를 최적 추정으로 적었다. **`elapsed` 키가 생긴 뒤 보드에 올라온 남의 항목 두 건이
그 추정을 깼다.**

| 출처 | score / rows | `elapsed` | rows/s | 결과 |
|---|---|---|---|---|
| `절세미남정호` (08-13 13:46) | 20000 / 9980 | 1499.8 | 6.654 | 통과 |
| `화이트해커30000` (08-13 22:23) | 30000 / 14980 | **1579.0** | **9.487** | 통과 |

`rows 14980`이 1579.0초에 통과했으므로 `r >= 9.487`이다. **`r = 9`라면 상한이 14211이라
거부됐어야 한다 — 반증이다.** 거부 최소값 9.756과 합치면:

```
r ∈ [9.4870, 9.7561)      ← 통과 최대 9.487 / 거부 최소 9.756
r = 9.5 로 관측 15건(통과 12 · 거부 3) 전수 검증 → 불일치 없음
```

`9.5`가 구간 안의 유일한 깔끔한 값이므로 이걸 최적 추정으로 삼는다(추정).
**안전 상수는 9.4/s를 쓴다** — `r >= 9.487`이 관측으로 보장되므로 9.4는 항상 안전하고,
이전에 쓰던 8.8보다 대기가 6% 짧아진다.

남의 항목을 근거로 쓰는 것이 타당한 이유는 `elapsed`가 **서버가 판정에 쓴 값 그대로**이기
때문이다(§1). 우리 프로브와 정확히 같은 품질의 데이터점이고, 오히려 우리가 도달하지 못한
큰 `rows` 구간을 채워 준다. 단 `admin_insert` 항목은 검증을 통과한 적이 없으므로 제외한다.

한편 게임의 실제 최대 전진 속도는 홉 0.13초 → 약 7.7행/초다. `r = 9.5`는 그보다 **23% 위**이므로,
서버는 "물리적으로 가능한 최대 속도"에 여유를 얹어 잡은 셈이다(추정).

### 두 검사를 합치면 — `score_max ≈ 18.8 * elapsed + 40`

속도 검사는 `rows`만, 정합성 검사는 `score`와 `rows`의 관계만 본다. 두 검사는 독립이므로
주어진 대기 시간에서 낼 수 있는 최대 점수는 `rows`를 상한까지 밀어붙였을 때다.

```
rows  <= 9.4 * elapsed          (속도, 안전 상수)
score <= rows * 2 + 40          (정합성)
⇒ score_max ≈ 18.8 * elapsed + 40
```

**여기서 실무적으로 가장 중요한 결론이 나온다 — `rows`를 절반으로 줄이면 대기가 절반이 된다.**
`score == rows`로 보내는 것은 안전하지만 같은 점수에 **두 배**의 대기를 지불하는 선택이다.

단, 합친 식만 만족시켜서는 안 된다. `120점 / rows 120 / 12.3초`는 합친 상한(261점) 아래였는데도
거부됐다 — `rows 120`이 12.3초가 허용하는 108행을 넘었기 때문이다. **두 조건을 따로 확인해야 한다.**

### 정합성 규칙의 형태 — `score <= rows * 2 + 40`

08-12에는 이 규칙을 `score <= rows * 2`로 적었다. **보드에 남은 남의 항목들이 그보다 40점
느슨하다는 것을 보여준다.** 아래 네 항목은 예외 없이 `rows * 2 + 40`에 **정확히** 붙어 있다.

| 닉네임 | score / rows | `rows*2 + 40` | 차이 |
|---|---|---|---|
| `t` | 340 / 150 | 340 | **0** |
| `t` | 640 / 300 | 640 | **0** |
| `t` | 1040 / 500 | 1040 | **0** |
| `불꽃미남정호` | 10000 / 4980 | 10000 | **0** |

네 개가 모두 경계에 정확히 앉아 있는 건 우연이 아니다 — 누군가 우리와 같은 분석을 하면서
`rows`를 최소화하는 방향으로 경계를 찾아냈고, 그 값이 `rows*2 + 40`이라는 뜻이다.
`+40`은 행당 보너스 `+2`의 20행분, 즉 스테이지 하나(20행) 몫으로 읽히지만 근거는 없다(추정).
`(rows + 20) * 2`로 쓰면 같은 식이 된다.

우리 쪽 관측은 이 식과 모순되지 않는다. 통과한 `440 / 220`은 `220*2+40 = 480` 아래이고,
거부된 `100 / 10`(상한 60), `10000 / 150`(상한 340), `10000 / 60`(상한 160)도 전부 설명된다.

| score / rows | 상한 `rows*2+40` | 결과 |
|---|---|---|
| 440 / 220 | 480 | `200 ok` |
| 1600 / 1580 | 3200 | `200 ok` |
| 10001 / 5001 | 10042 | `200 ok` |
| 100 / 10 | 60 | `403 inconsistent` |
| 10000 / 150 | 340 | `403 inconsistent` |
| 10000 / 60 | 160 | `403 inconsistent` |

우리 관측만으로 확정된 것은 **2.0배가 통과하고 10배는 거부된다**는 것이고, `+40` 항은
남의 항목 네 개에서 온 추론이다. 목표 점수에 대해 `rows = ceil(score/2)`로 잡으면
어느 쪽 해석에서도 안전하고, 대기 시간 차이는 0.5% 미만이다.

`2.0`이라는 계수는 게임 로직과 정확히 맞물린다 — 보너스는 니어미스 1회당 `+2`이고
니어미스는 플레이어가 그 행에 있는 동안에만 판정되므로, 현실적 상한이 행당 `+2`다
(`row.gd` `_step_entities`, `NEAR_DIST = 84`). 즉 서버는 `score - rows <= rows + 40`을
검사하는 것으로 보인다(추정). 뒤집으면 **"칸수는 적은데 보너스로 점수만 부풀리기"는
2배까지만 허용된다**는 뜻이고, 바로 그 2배가 대기 시간을 절반으로 깎는 지렛대다.

### 목표 점수별 필요 대기 시간

속도 검사가 `rows`를 보므로 **대기 시간은 `score`가 아니라 `rows`로 결정된다.**
안전 상수는 `rows <= 9.4 * elapsed`를 쓴다(관측이 보장하는 `r >= 9.487`보다 약간 보수적).
`rows`는 정합성 하한 `ceil((score-40)/2)`로 잡은 값이다 — 이게 대기를 최소화한다.

| 목표 점수 | rows(하한) | 안전 대기(9.4행/s) | `score==rows`로 보낼 때 | 실측 |
|---|---|---|---|---|
| 1,004 | 482 | 51초 | 107초 | 150초 통과 (rows 1004) |
| 3,000 | 1,480 | 158초 | 319초 | 490초 통과 (rows 3000) |
| 10,001 | 4,981 | 530초 | 1,064초 | 565.6초 통과 (rows 5001) |
| 20,000 | 9,980 | 1,062초 | 2,128초 | 1,499.8초 통과 ※ |
| 30,000 | 14,980 | 1,594초 (26.6분) | 3,192초 | **1,579.0초 통과** ※ |
| 100,000 | 49,980 | 5,317초 (88.6분) | 10,634초 | 미시도 |

※ 남의 항목에서 읽은 값(§3 표 참조).

08-12 문서가 적어 둔 "10000점 = 26분"은 `score` 기준으로 계산한 값이라 **두 배 과대평가**였다.
`rows`를 절반으로 두면 9분이면 된다 — 실제로 그렇게 통과했다.

`r`의 하한이 8.84에서 9.487로 올라간 덕에 이 표의 값은 이전 판보다 6% 짧아졌다.
`r`을 다시 좁힐 데이터가 나오면 이 표부터 다시 계산해야 한다.

## 4. 그래서 어떻게 탐색하는가

거부는 흔적을 남기지 않고, **토큰은 세션에 묶여 있지 않다** — `GET api/start`는 인증이 없고,
여러 개를 미리 받아 병렬로 숙성시킬 수 있다. 이 두 성질을 합치면:

> 토큰을 미리 대량 발급해 두고, **목표 점수를 고정한 채 토큰 나이를 늘려가며 재시도**한다.
> 실패는 비용이 0이고, 첫 성공이 곧 목표 달성이다.

중간 점수로 경계를 이진 탐색하면 성공할 때마다 보드에 쓰레기 항목이 남는다. 목표 점수 자체로
탐색하면 그 문제가 사라진다.

| 스크립트 | 용도 |
|---|---|
| `tools/submit_target.py <score> <name> [char] [ages] [rows]` | 목표 1개를 나이 스케줄대로 재시도. 기본 `480,600,720`초. 3000점과 10001점을 이걸로 등록했다. **`rows`를 반드시 넘겨라** — 생략하면 `score`와 같아져 대기가 두 배가 된다 |
| `tools/submit_run.py` | 08-12 세션의 2단(1004 → 10000) 스케줄러. 상수가 하드코딩되어 있고 기록용으로 남겨 둔다 |
| `tools/board_probe.py <대기초> <score> [rows] [name] [char]` | 단발 프로브 |

### 검증 관련 실무 주의

- **`rows = ceil((score - 40) / 2)`로 보내라.** 속도 검사가 `rows`만 보므로 이게 대기 시간을 절반으로 줄인다(§3). `score == rows`는 안전하지만 두 배 기다리는 선택이다. 반대 방향, 즉 `rows`를 그보다 더 깎아 점수를 부풀리는 건 정합성 검사에 막힌다. `+40` 항을 신뢰하지 않겠다면 `ceil(score/2)`를 쓴다 — 대기 차이는 0.5% 미만이다.
- **재시도에는 매번 새 토큰이 필요하다.** 거부된 시도도 토큰을 소진시킨다(§2). 스케줄러가 토큰을 미리 여러 개 발급해 두는 이유다.
- **토큰 나이 측정은 로컬 시계로 하지 마라.** 서버 epoch이 로컬보다 약 2초 앞서 있었다. `now_local - token_ts`로 계산하면 나이를 과소평가한다. 토큰 수신 시각을 `time.monotonic()`으로 잡고 **경과 시간**을 재는 게 맞다(시계 오차가 상쇄된다). 이제는 성공 응답의 `elapsed` 키에 **서버가 직접 잰 나이**가 담겨 오므로(§1), 경계를 다룰 때는 그 값을 정본으로 쓰면 된다 — 우리 측정 565.6초와 서버의 `565.6`이 일치했다.
- **TTL 하한은 1,579초(26.3분).** 우리 제출로는 565.6초까지였지만, `화이트해커30000`의 `elapsed = 1579.0`이 그 나이의 토큰이 정상 판정까지 도달했음을 보여준다. **남의 성공 항목의 `elapsed`가 곧 TTL 하한 관측치**라는 점이 이 필드의 부수 효과다. 그보다 오래 묵힌 토큰이 유효한지는 미확인이며, 만료가 있다면 `too_fast`가 아닌 다른 에러가 돌아올 것이므로 스케줄러는 예상 외 에러에서 즉시 중단하도록 되어 있다.
- **점수 상한은 30000까지 없다.** `rows`가 속도 조건을 만족하면 통과하며, 그 아래에 절대 상한이나 stage 상한은 없다. `rows 14980 → stage 749`도 정상 저장됐다. stage에 상한이 없는 것은 게임 쪽과도 일치한다 — `ThemeDefs.stage_index()`(theme_defs.gd:86)에 클램프가 없고 테마는 `% s.size()`로 순환하며, `loop_count()`가 테마 목록을 몇 바퀴 돌았는지 세도록 따로 있다. `?s=N`의 500 클램프는 URL 파라미터에만 걸린다.
- **서버가 지금 수정되고 있다.** `elapsed` 키는 08-13 01:06과 13:13 사이에 생겼다. 08-12에 측정한 규칙이 오늘도 유효하다고 가정하지 말고, 최신 데이터점과 어긋나면 최신 쪽을 믿어라.

## 5. 정적 분석에서 이미 알던 것 (재확인)

- `token`을 제외한 **모든 필드는 클라이언트가 만든 값**이다. `name`은 길이·문자셋 검사가 UI(`max_length=12`)에만 있어 임의 닉네임 사칭이 가능하다 — 실제로 여러 사람이 `핵정호`, `바이브정호` 등으로 등록되어 있다.
- `char`도 임의 문자열이 들어간다. 화이트리스트 검사는 **읽는 쪽**(ui.gd:467)에서만 한다.
- `?s=N`(스테이지 스킵)은 `start_row`가 점수에서 차감되므로 **점수 부풀리기에 쓸 수 없다**.
- 로컬 `user://save.json`의 `best`는 서버로 전송되지 않으므로 리더보드와 무관하다.
- **공개 API에 삭제 엔드포인트가 없다.** 우리가 등록한 점수는 회수할 수 없다. 단 운영자에게는 별도 경로가 있다 — `admin_insert` 플래그가 그 증거이므로, 우리 항목이 언제든 지워질 수 있다고 봐야 한다.

## 6. 2026-08-14 패치 — 관문은 바디의 직렬화 형태였다

`화이트해커30000`이 **운영자 본인**이었다. 22:23:18에 30000점을 직접 올려 취약점을 재현해
보이고, 22:26~22:35에 라벨이 붙은 프로브 5건(`cX350`, `cExp`, `g_l120`, `g_l240`, `g_exp`)으로
한도를 재고, 그 뒤 패치했다. 즉 이 패치는 사고가 아니라 의도된 방어다.

### 무엇이 바뀌었나

| 변화 | 내용 |
|---|---|
| `api/start` 응답 | `{"token": ...}` → `{"token": ..., "seed": "<16자리>"}`. **다만 `seed`는 제출에 필요하지 않다** — 실제 클라이언트는 그것을 읽지도, 되돌려주지도 않으면서 통과한다 |
| 거부 응답 | `too_fast`/`inconsistent`/`token:reused`가 전부 `{"ok": false, "error": "rejected"}`로 통일. 어느 검사에 걸렸는지 감춘다 |
| 새 힌트 | 대부분의 거부에 **`"hint": "stale"`**. 소진 토큰 재사용만 `hint` 없이 `rejected` |
| `api/start` 제한 | 연속 호출 시 `{"error": "too many starts"}` — 발급에도 IP 단위 제한이 붙었다 |

### 진짜 관문 — Godot의 JSON 직렬화 형태를 지문으로 쓴다

**`stale`은 "토큰이 낡았다"가 아니라 "클라이언트가 낡았다/가짜다"였다.**

Godot의 `JSON.stringify`는 `sort_keys`가 기본 `true`이고 구분자에 공백을 넣지 않는다.
따라서 `ranking.gd:97`이 만드는 바디는 **항상** 이 형태다.

```
{"char":"peccy","name":"무명고라니","rows":2,"score":2,"token":"1786636135...."}
   ↑ 키가 알파벳 순(char, name, rows, score, token)   ↑ 콜론·콤마 뒤 공백 없음
```

우리 스크립트는 `json.dumps`를 기본값으로 써서 **삽입 순서(`name, score, rows, char, token`)에
`", "`·`": "` 공백**을 넣어 보냈다. 서버는 그 차이만으로 거부한다. 실제 게임은 아무 영향이 없고
스크립트만 걸리는, 값싸고 효과적인 방어다.

정본 구현은 `tools/submit_target.py`의 `godot_json()`이다.

```python
json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**이 함수의 구분자나 정렬을 "정리"하지 말 것.** 그게 통과 조건 자체다.

### 어떻게 찾았나 — 실제로 플레이해서 성공 요청을 캡처했다

추측으로는 못 찾았다. 다음 가설을 전부 배제한 뒤에도 막혀 있었다.

| 가설 | 검증 | 결과 |
|---|---|---|
| 토큰 TTL 초과 | 나이 **0.0초** 토큰 | `stale` |
| 뒤 토큰이 앞을 무효화 | 토큰1 발급 → 토큰2 발급 → 토큰1 사용 | `stale` |
| `seed` 미전송 | 문자열 에코 / **정수 에코** / `sig=sha256(token+seed)` | `stale` |
| 스크립트 지문(헤더) | 크롬 `UA`·`Origin`·`Referer`·`Accept-Language` 위장 | `stale` |
| 세션 쿠키 | `/`·`api/start`·`api/scores`에서 `Set-Cookie` 탐색 | 쿠키를 발급하지 않음 |
| 새 엔드포인트 | 19개 경로 탐색 | 전부 404 |
| 누적 IP 상태 | 10분 완전 침묵 후 깨끗한 단발 시도 | `stale` |
| 점수/행 비율 | `score==rows` vs `score==rows*2`(운영자 프로브와 동일 형태) | `stale` |
| 새 클라이언트 배포 | `index.pck` 재다운로드 → **SHA-256이 08-12 사본과 완전 일치** | 변경 없음 |

전환점은 **Playwright로 게임을 실제로 플레이한 것**이다. 페키를 골라 14홉을 뛰고 기차에 치여
2점으로 죽은 뒤 "랭킹 등록"을 눌렀더니 **`등록 완료!`** 가 떴다. 즉 관문은 진짜 클라이언트와
합성 요청을 구분하고 있었고, 그 성공 요청을 `browser_network_request`로 캡처해 바디를
바이트 단위로 비교하자 차이가 키 순서와 공백 하나로 좁혀졌다.

**교훈: 서버가 "무엇을" 거부하는지 알 수 없을 때는, 정상 클라이언트가 성공하는 요청을 한 번
캡처하는 것이 추측 100번보다 빠르다.** 이 게임은 클라이언트를 우리가 통제할 수 있으므로
언제든 정답 샘플을 만들어낼 수 있었는데, 그걸 마지막에야 했다.

### 새 응답 어휘 해독 — `hint`의 유무가 유일한 단서다

거부가 전부 `rejected`로 통일됐지만 **`hint` 필드의 유무가 두 계열을 가른다.**

| 응답 | 의미 | 근거 |
|---|---|---|
| `403 {"error": "rejected"}` — **`hint` 없음** | **토큰 문제.** 소진되었거나 만료되었거나 서버가 모르는 토큰 | 소진 토큰 재사용이 이 형태였고, 한 번도 쓰지 않은 3,976초 된 토큰도 같은 형태를 받았다 |
| `403 {"error": "rejected", "hint": "stale"}` | **바디 형태 또는 점수 검증 실패** | 잘못 직렬화한 요청, 그리고 올바르게 직렬화했지만 18.18점/초였던 요청이 이 형태 |

이 구분이 진단의 핵심 도구다. `hint`가 없으면 토큰을 새로 받아야 하고, `hint: stale`이면
바디 형태와 점수 조건을 봐야 한다. **`hint`를 로그에 남기지 않으면 두 원인을 영원히 혼동한다.**

### 토큰 TTL과 점수 한도의 실측 구간

패치 후 두 개의 새 상한이 확인됐다. 둘이 서로 반대 방향으로 창을 좁힌다.

```
TTL:      1,579초 유효(화이트해커30000)  <  TTL  <  3,976초 만료(우리 토큰, hint 없음)
점수 한도: 10.0점/초 통과(200점 @20초)   <  한도  <=  18.18점/초 거부(30001점 @1,650초)
```

목표 점수 `S`, `rows = ceil((S-40)/2)`에 대해 세 조건을 동시에 만족해야 한다.

```
age >= rows / 9.4          (행 속도, §3)
age >= S / 10              (점수 한도, 안전하게 하한값 사용)
age <  3,976               (TTL 상한)
```

30001점이면 `age ∈ [3000, 3976)`이고, 여유를 둔 **3,300초(9.09점/초)** 가 적정값이다.
점수 한도가 실제로 10보다 높다면 창은 더 넓어지지만, 확인된 값으로만 계산하는 게 맞다.

**함의: 점수가 커지면 창이 닫힌다.** `S/10 < 3,976`이어야 하므로 이 규칙 아래에서
등록 가능한 상한은 대략 **39,760점**이다. 그보다 큰 점수는 TTL 안에 필요한 나이를
확보할 수 없다 — 운영자가 의도한 설계로 보인다(추정).

### 진단 설계에서의 오판

초기 프로브를 전부 "속도 검사에서 반드시 떨어지도록"(`rows`를 과도하게) 만들어 흔적을 없애려
했는데, 그러면 **운영자가 거부 응답의 이름만 바꾼 경우와 구분할 수 없다.** 한동안 "속도 한도가
조여졌다"고 오판했다. 거부 응답만으로 진단할 때는 **반드시 통과해야 하는 요청**을 하나 섞어라.
통과가 기대되는 요청이 거부되면 그것이 관문의 존재를 증명한다. 통과할 값을 보드 컷오프
아래로 잡으면(예: 120점, 200점) 성공해도 보이는 리더보드를 오염시키지 않는다.

### 점수 한도는 조여지지 않았다

운영자 프로브의 `g_l120`(720 @ 120.8s)·`g_l240`(1440 @ 241.5s)이 정확히 `score = 6 * elapsed`여서

직렬화를 고친 뒤 `200점 / rows 100`을 토큰 나이 20초(=**10.0점/초**)에 보냈더니 통과했다.
따라서 6점/초 규칙은 적용되지 않았고, §3의 `rows` 기준 규칙이 그대로 유효하다.

`main.gd`가 타이틀·게임오버·타이틀복귀에서 `start_run()`을 호출하므로 **토큰은 플레이 시작 전에

### 서버는 trace를 재현해 rows를 계산한다

프록시로 실제 플레이의 토큰·trace·ticks를 유지한 채 필드만 바꿔 가며 확인했다.

| 조작 | 결과 |
|---|---|
| `score` 2 → 4 (rows 2 그대로) | **통과** — 점수는 재계산하지 않는다 |
| `rows` 2 → 500 (ticks 251) | 거부 |
| `rows` 0 → 500, trace 0건, ticks 4231 | 거부 |
| `rows` 0 → 500 + **정합적 합성 trace 500홉** (12틱 간격, ticks 6087, 나이 120초) | 거부 |
| `rows` 5 → 20 + 합성 trace 20홉 (사람이면 쉬운 범위) | 거부 |

정합성만 맞춘 합성 트레이스가 크기와 무관하게 전부 거부되는데 점수 부풀리기는 통과한다.
즉 **서버는 시드로 trace를 재현해 `rows`를 직접 계산하고, 제출된 `rows`가 그것과 맞는지 본다.**
`score`에만 `rows * 2 + 40`의 여유가 남아 있다. 응답 엔트리에 새로 붙은
**`"verified": true`** 가 이 검증의 결과 표시로 보인다(추정).

### 실무적 결론

```
등록 가능한 점수 = (실제로 넘은 행 수) * 2 + 40
```

**대기 시간으로 점수를 사는 방법은 이 패치로 끝났다.** 목표 점수 `S`를 위해서는
`rows >= (S-40)/2` 행을 **실제로 통과**해야 한다 — 1,000점이면 480행, 30,001점이면 14,981행이다.
남은 자유도는 점수 2배 여유와 닉네임뿐이다.

`hint` 해독도 갱신된다. `v:3`이 없으면 `hint: "stale"`(낡은 클라이언트), 토큰이
소진·만료면 `hint` 없는 `rejected`, 트레이스 재현 실패도 `hint` 없는 `rejected`다.

|---|---|---|
| `야호정호 602` (rows 562) | **0** | 정상 |
| `호호호 502` (rows 502, elapsed 107.5) | **3** | 계산으로 만든 입력 흔적 |
| `사랑해요정호님 200` 4건 | **3 / 2** | **위조 시도 이력** + 기계적 입력 |
| `뚫었어요정호님 300` 2건 | 3 | 위조 시도 이력 + 기계적 입력 |
| `훗훗훗 287 / 178 / 166` | 0 | 정상 |
| `hj 203` | 2 | 사람 손으로 보기 어려운 입력 패턴 |

**`사랑해요정호님`으로 보낸 `503점 / rows 240` 부풀리기(§8.1)가 그 닉네임의 모든 항목에
"위조 시도 이력"으로 남았다.** 거부된 제출은 보드에 항목을 남기지 않지만 **흔적은 남는다.**
반면 한 번도 위조하지 않은 새 닉네임 `야호정호`는 정상 판정을 받았다.

> **실무 규칙: 최종 등록에 쓸 닉네임으로는 절대 실험하지 마라.** 프로브·경계 탐색은 버릴
> 닉네임으로 하고, 목표 등록은 깨끗한 새 닉네임으로 한다. 되돌릴 방법이 없다.

`호호호 502`(운영자 본인으로 추정, §6)가 `rep 3`인 것도 함께 읽어야 한다 — `score == rows`로
보너스가 정확히 0이고 4.67행/초를 502행 유지한 기록이라, 서버 자신의 판정으로도
"계산으로 만든 입력"이다. **즉 이 판정은 자동이고 예외가 없다.**

### 9.3 무엇이 `rep 0`을 받았나

`야호정호 602`는 체크포인트 탐색으로 조립한 경로다([`autopilot.md`](autopilot.md) §8).
그런데도 정상 판정을 받은 조건은 다음과 같다(추정 — 서버 코드는 없다).

- **모든 입력이 실제 엔진 주행에서 나왔다.** 합성 입력을 trace에 끼워 넣지 않았다.
- **점수를 부풀리지 않았다.** `score()`·`rows_crossed()`를 그대로 보냈다.
- **홉 간격이 8~9틱으로 흔들린다.** 완전히 고정된 8틱 연사가 아니다.
- **첫 입력이 55~150틱 뒤다.** 1틱 입력은 사람에게 물리적으로 불가능하다.
- **그 닉네임에 위조 이력이 없다.**

어느 조건이 결정적인지는 분리하지 못했다. 다만 `hj 203`이 `rep 2`("기계적 입력 패턴")를
받은 것을 보면 **입력 타이밍만으로도 걸린다.**
